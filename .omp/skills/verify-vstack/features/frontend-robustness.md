# Frontend content robustness

Break-ui's visible Utility description supplies realistic adverse-content guidance to main-session implementation and delegated UI work. Good-css has no content-guidance hand-off. Native selection and instruction following remain unproven pending explicitly approved remote evaluations. This recipe observes adverse data, authorized fixes, and usable results through the existing native frontend and browser seams.

## Sub-features

- `frontend-robustness-main`: main-session implementation applies realistic content guidance to actual frontend edits.
- `frontend-robustness-worker`: an existing delegated UI worker reaches the same guidance and performs the edits.
- `frontend-robustness-browser`: adverse input reveals a visible failure before fixes, and real controls establish the corrected outcome.
- `frontend-robustness-package`: public source, load, and packaging interfaces account for the shipped adaptation and notice.

## How to get to it (user POV)

- Start the existing implementation entry on data-bearing UI, including narrow layouts, missing fields, long values, and collection boundaries.
- Delegate the same work to the existing vstack-worker role. Leave UI Utility names out of its brief to test description selection. Its good-css requirement covers CSS only.
- Use the project's existing Verify owner to exercise resulting behavior. No extra UI entry flow or independent audit executor is involved.

- Follow `frontend-guidance.md` for Doctor, native real-HOME isolation, caller Session model, full-package loading, provenance, and recording. Keep each process fresh and capture saved native histories, not stub echoes.

- Browser opens always use a unique name, `app: "chromium"`, and an explicit viewport. Record the returned backend and engine. Retain full-resolution lossless WebP and ARIA using `../SKILL.md`, and close only owned tabs and servers.

### Browser actions and boundaries

For each resulting main and delegated app:

1. Step `frontend-robustness-worst-case`: Select Worst case at the real container width and 320px. Confirm full identifying values remain available, actions remain inside the viewport, tall scripts and emoji render, and user markup stays literal. Capture the visible long-label action.
2. Step `frontend-robustness-action`: Activate that action and record the matching member removal and status, plus the updated count. Test the keyboard path and focus after removal.
3. Step `frontend-robustness-collections`: Select Empty and One. Observe the empty message, singular count, and a usable one-member action. Select 1,284 rows and verify the full formatted total, bounded rendering or actual scrolling behavior, pagination if present, and final-page navigation. Include the applicable page-size and page-size-plus-one cases through the same data boundary.
4. Step `frontend-robustness-persistence`: Reload a selected state to verify URL persistence. Return to Demo to catch a fix that regresses ordinary content.
5. Step `frontend-robustness-layout`: Observe the widest supported layout and text growth. Label root-font-size enlargement as a proxy, not actual 200% browser zoom. Check supported dark and RTL modes. Record unsupported environments, physical-touch limitations, and unexercised engines explicitly.
6. Step `frontend-robustness-capture`: Retain actions, geometry when useful, runtime errors, ARIA, and lossless screenshots. Do not substitute hidden-pointer checks, computed CSS alone, or a final rendering for action evidence.

## Gotchas

- The dataset selector is development evidence, not a production feature requirement. Reuse the existing fixture boundary and avoid a new test-only product interface.
- Audit-only requests stop at findings; implementation with already-authorized fixes continues under the existing owner.
- Keep this demonstration scoped to content robustness. The companion recipes cover motion and mobile behavior. Inspect actual Utility selection and relevant reference reads rather than assuming good-css supplies them.
- A preserved source catalog does not establish support for any library or browser. Verify APIs against actual installed versions, and report only exercised scenarios.
- Keep baseline failures and unsuccessful captures. Never relabel a good baseline UI as a failed one or a text-growth proxy as browser zoom.
