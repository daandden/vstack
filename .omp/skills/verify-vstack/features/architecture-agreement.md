# Architecture agreement

The grill assesses each change, expands only consequential unsettled choices, records visual agreement, and stops before implementation. This recipe evaluates the actual reasoning at the user-visible Matt-run seam. It does not use the scripted model driver as proof of those decisions.

## Sub-features

- `architecture-assess` covers one-module trust or durability choices, mechanical many-file changes, and applicable settled patterns.
- `architecture-ground` covers changed pattern assumptions, missing facts, speculative quality concerns, credible quality scenarios without production benchmarks, and greenfield context.
- `architecture-compare` covers comparable visual alternatives, screening, trade-offs, recommendations, and a forced single viable shape.
- `architecture-brief` covers responsibilities, interactions, guarantees, constraints, costs, rationale, rejected alternatives, and decision provenance without coding details or scaffolds.
- `architecture-consent-stop` covers real explicit answers, non-consent, the summary-only close, and the user-invoked handoff.
- `architecture-handoff` consumes separate to-spec and implementation evaluation evidence to check preservation of agreement and consequential gap handling. A grill-only run does not prove those entry points.

## How to get to it (user POV)

- Start `/skill:grill-with-docs` with a change and its applicable decisions.
- Answer the consequential choices through the existing Flow questions. Read the Architecture brief or lightweight assessment and closing summary.
- Invoke `/skill:to-spec` yourself for a larger change. Its separate proof must inspect the self-contained isolated publication and a newly discovered fork without publishing a silently selected design.
- Invoke `/skill:implement` or `/skill:implement-spec` yourself. Their separate proof must distinguish ordinary implementation choices from a departure that changes an agreed guarantee.

## Driving it with actual skill evaluations

Preconditions: the user-visible Matt-run seam is confirmed by the spec or user. Read `$CHECKOUT/plugin/skills/skill-creator/references/evaluation.md` and use its isolated evaluation procedure, Session model/thinking discovery, skill snapshot, and runtime isolation. Use its Headless batch protocol for non-interactive cases. Use the actual TUI procedure below for cancellation, timeout, and empty responses. Keep the real `HOME` for credentials. The stub home's Doctor and `scripts/drive.ts` are not this recipe's launcher. No model substitution, package installation, production tracker writes, or source implementation is authorized by this recipe.

1. Create a new evidence directory under the supplied Scratch dir. Snapshot the pre-change grill before editing when available. Record when no pre-change behavioral run exists. Create independent scenario inputs containing the change, surrounding context, and applicable prior decisions, not expected answers. Preserve an input checksum inventory.
2. Use the evaluation reference's launch command for each with-skill and baseline run. Name the selected skill's absolute `SKILL.md` path. Keep inputs, `outputs/`, the overlay, and session transcripts in separate per-case run directories. Ignore the installed grill and include the union of skill dependencies on both sides. Inspect discovery in the actual runtime with that overlay before judging isolation. A registry listing that ignores runtime overlays does not establish it.
3. Headless runs use a dedicated `--home <outputs>/flow-home` for their non-question Flow commands. Interactive picker runs instead keep CLI and extension in the same real-HOME namespace, as the TUI procedure below requires. Use each run's own session and agent identity. Never bind to the producer's real Flow or publish to a production tracker. Tell Headless runs to label recommendations as non-consent. Save stdout, stderr, exit code, command, model, thinking level, prompts, overlays, transcripts, and captured Flow artifacts.
4. Drive the scenarios below through the selected grill. Grade actual decisions and artifacts against the stated requirements, not instruction strings, exact wording, artifact names, or bare file existence. Model-run findings are observed evaluations, not deterministic unit-test guarantees.

| Scenario input | Observable proof |
|---|---|
| One module has an unsettled tenant-isolation or acknowledged-write durability choice. | The assessment identifies the affected guarantee and expands despite the small edit. |
| A behavior-preserving rename touches many callers. | The assessment grounds no expansion without a new brief or compulsory diagram. |
| An ordinary feature follows an accepted pattern with unchanged access, lifecycle, and failures. | The assessment records the pattern's fit without repeating settled choices. |
| A provider keeps the same method shape but changes residency or recovery obligations. | The grill checks assumptions and exposes the real consequence rather than treating signatures as equivalence. |
| The user proposes caching for vague future speed and has not read the existing path. | Grounding investigates actual facts and clarifies requirements without inventing a scale target. |
| A credible workload or crash scenario establishes an important guarantee, without production measurements. | Analysis can reveal a real trade-off. Missing benchmarks alone do not dismiss it. |
| Greenfield work has either settled local-only context or consequential local-versus-hosted constraints. | Context, not greenfield status, determines expansion. No investigation of nonexistent code is required. |
| A consequential fork has genuinely different viable shapes. | Captured comparable visuals, screening, explicit accepted costs, rejected alternatives, and a recommendation support the question. |
| Signed constraints leave only one shape but recovery consequences remain unagreed. | The shape and exclusions are explained without fabricated viable alternatives. The remaining consequence still needs agreement. |
| Prior explicit answers settle an expanded direction. | The Architecture brief preserves the actual guarantees, interactions, ownership, constraints, rationale, costs, and provenance. It leaves signatures and private coding choices to implementation. |
| No live answer is available, or an actual tool response reports cancellation, timeout, or an empty response. | The corresponding decision stays unresolved. Automatic picks and recommendations are not called user agreement. Preserve the actual response status rather than fabricating a timeout or cancellation. |

5. For page proof, inspect the relevant live or static Flow in the browser. Check the assessment and agreement content, question-level visual needs, actual diagrams, and answer provenance. Preserve the ARIA snapshot and full-resolution lossless WebP through the Verify skill's Evidence step 5. An unavailable browser check is missing proof, not a passed visual review.
6. Run the live smoke separately with the user present. Start a fresh interactive TUI with a disposable grill scenario, a real consequential choice, and no implementation or publication authorization. Use `flow_ask` once to publish the generated question, alternatives, trade-offs, recommendation, and necessary visuals and open the actual omp-tools picker. Preserve the actual human answer and its separately recorded provenance, continue to the brief and summary, then observe the stop. Record the file inventory and transcript showing no source implementation, scaffold commit, automatic next-skill invocation, or tracker publication. Headless recommendations and automated keyboard answers cannot satisfy this step.
7. If this worker cannot obtain the live answer, return the exact generated question, complete options and context, artifact paths, missing decision, and evidence of held dependent work to the parent. Do not claim the live smoke passed. Preserve the held run and patch for continuation with the actual answer.
8. Collect to-spec and implementation consumers' separate proof when evaluating the whole feature. Record which entry point each input exercised. Inspect the canonical isolated spec for embedded necessary visuals and agreement, and inspect gap scenarios for held synthesis or exposed departures. Do not infer those results from the grill's close.
9. Stop only the isolated Flow hosts this evaluation started through their authenticated `host stop --home <isolated-home>` commands. Keep the scenario inputs, outputs, session transcripts, artifacts, and failure evidence. Report each observed result, baseline comparison, limitation, unexercised case, and live checkpoint separately.

### Drive current-picker non-consent

These are automated controller cases at the same Matt-run seam, not live human agreement. Keep historical native RPC proof and human confirmation proof separate. Neither proves the current picker route.

1. Snapshot the selected skills and source hashes. Create independent scenarios with genuine unsettled consequential choices. Supply facts and applicable decisions, not a future cancellation, timeout, or expected answer. Neutral case paths must not disclose the controller policy.
2. Use skill-creator's Session model and thinking discovery. Set `skills.customDirectories` to `$CHECKOUT/plugin/skills`, disable memory, ignore the installed skill under test and its wildcard form, and include its dependencies. Set both `PI_CONFIG_FILES` and `--config` to the overlay. The helper loads the checkout package and the explicitly named omp-tools package in a fresh TUI. It retains real HOME and credentials but clears inherited session variables.
3. Read `flow-page.md`'s current-picker prerequisites. The named omp-tools must install `Symbol.for("omp-tools.host-ask-dialog")` in an interactive TUI. CLI publication and the extension must use the same HOME, checkout, child session, and main-agent binding. Do not pass an isolated `--home` to the model's CLI while `flow_ask` reads real HOME. Permit only owned disposable Flow state and scenario output, never the parent's Flow or production tracker writes.
4. Launch `scripts/flow-ask-tui.py` as SKILL.md specifies, with `--prompt`, `--config`, and `--case cancelled|timeout|empty`. No stub provider is used in this mode. Keep each launch's new case directory, source hashes, overlay, persistent session, terminal bytes, keyboard events, and raw `flow_ask` tool results.
5. Cancellation sends Escape only after the actual picker appears. Timeout sends no answer and uses the real configured `ask.timeout` in the case overlay. A controller deadline or process failure is not a picker timeout. Empty response navigates to the real picker's Submit review without choosing an option, then submits. That requires a multi-question or multiselect round with a Submit tab. If the generated round has no such tab, report that prerequisite rather than changing it to a selected answer.
6. Inspect the actual returned status and raw `response.results`, including `selectedOptions` and `timedOut`. Preserve the original question contribution and receipt. The model records each normalized answer later through CLI `submit`; the tool itself authors no answers. Empty selection alone establishes neither cancellation nor timeout. Missing TUI routing is unavailable, not non-consent of another kind.
7. Grade the actual questions, answers, Results, close, transcript, and file inventory. Consequential choices stay unresolved or explicitly non-confirmed. A brief separates facts and proposals from agreement. No automatic pick becomes a decision. Dependent work stays held without source scaffolds, implementation, spec publication, tracker writes, or automatic next-skill invocation. If the turn cannot produce a blocked close, preserve it separately from any explicitly labelled no-new-decision continuation.
8. Inspect each relevant Flow projection in the real browser. Preserve ARIA and full-resolution lossless WebP. Keep failed attempts and unavailable routes, not just successful cases. Stop only owned native processes and owned Flow hosts, and copy their Flow exports before cleanup. The helper stops its own omp process; the evaluator owns Flow closure and authenticated host cleanup.

`summary.json` reports transport completion, not behavioral acceptance. A missing current-picker round trip, uninspected consumer output, or unavailable browser leaves that coverage incomplete.

## Gotchas

- Skill-load and trigger checks prove selection, not architecture reasoning. A stub model's scripted answer proves neither the assessment nor human consent.
- A Headless run has no human answer even when it reaches a summary. An Architecture brief cannot convert its substituted picks into agreement.
- A prior explicit answer can drive a continuation evaluation, but does not substitute for the live confirmation-and-stop smoke.
- A failed process or unavailable dependency makes that proof unavailable. Keep its raw error and do not grade it as success.
- A baseline may also handle a scenario correctly. Report that observation instead of claiming the changed instructions caused it.
- Tests of exact wording or source strings cannot distinguish these consumer-visible failures. Keep evaluation fixtures and grading outside production tracker writes and unrelated source changes.
