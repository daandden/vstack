# Architecture agreement

The grill assesses each change, expands only consequential unsettled choices, records visual agreement, and stops before implementation. This recipe evaluates the actual reasoning at the user-visible Matt-run seam. It does not use the scripted model driver as proof of those decisions.

The canonical policy is [ADR 0053](../../../../docs/adr/0053-architecture-agreement-belongs-in-the-grill.md). Its renumbering preserves the accepted policy bytes. Published main owns ADR 0051 (UI guidance) and ADR 0052 (Stage-tab reading).

## Sub-features

- `architecture-assess` covers one-module trust or durability choices, mechanical many-file changes, and applicable settled patterns.
- `architecture-ground` covers changed pattern assumptions, missing facts, speculative quality concerns, credible quality scenarios without production benchmarks, and greenfield context.
- `architecture-compare` covers comparable visual alternatives, screening, trade-offs, recommendations, and a forced single viable shape.
- `architecture-brief` covers responsibilities, interactions, guarantees, constraints, costs, rationale, rejected alternatives, and decision provenance without coding details or scaffolds.
- `architecture-consent-stop` covers real explicit answers, non-consent, the summary-only close, and the user-invoked handoff.
- `architecture-handoff` consumes separate to-spec and implementation evaluation evidence to check preservation of agreement and consequential gap handling. A grill-only run does not prove those entry points.

## How to get to it (user POV)

- Start `/skill:grill-with-docs` with a change and its applicable decisions.
- Answer the consequential choices through the existing Flow questions. Read the Architecture brief or lightweight assessment and closing summary.
- Invoke `/skill:to-spec` yourself for a larger change. Its separate proof must inspect the self-contained isolated publication and a newly discovered fork without publishing a silently selected design.
- Invoke `/skill:implement` or `/skill:implement-spec` yourself. Their separate proof must distinguish ordinary implementation choices from a departure that changes an agreed guarantee.

## Driving it with actual skill evaluations

Preconditions: the user-visible Matt-run seam is confirmed by the spec or user. Read `$CHECKOUT/plugin/skills/skill-creator/references/evaluation.md` and use its isolated evaluation procedure, Session model/thinking discovery, skill snapshot, and runtime isolation. Use its Headless batch protocol for non-interactive cases. Use the actual TUI procedure below for cancellation, timeout, and empty responses. Keep the real `HOME` for credentials. The stub home's Doctor and `scripts/drive.ts` are not this recipe's launcher. No model substitution, package installation, production tracker writes, or source implementation is authorized by this recipe.

1. Step `architecture-agreement-inputs`: Create a new evidence directory under the supplied Scratch dir. Snapshot the pre-change grill before editing when available. Record when no pre-change behavioral run exists. Create independent scenario inputs containing the change, surrounding context, and applicable prior decisions, not expected answers. Preserve an input checksum inventory.
2. Step `architecture-agreement-launch`: Use the evaluation reference's launch command for each with-skill and baseline run. Name the selected skill's absolute `SKILL.md` path. Keep inputs, `outputs/`, the overlay, and session transcripts in separate per-case run directories. Ignore the installed grill and include the union of skill dependencies on both sides. Inspect discovery in the actual runtime with that overlay before judging isolation. A registry listing that ignores runtime overlays does not establish it.
3. Step `architecture-agreement-isolated-home`: Use a dedicated explicit `--home <outputs>/flow-home` on every development Flow CLI command, including publication, recovery, export, closure, and host cleanup. The interactive helper chooses `<new-case>/flow-home` and records it in `launch.json`. Keep real HOME only for Session credentials and the native TUI. Its normal-HOME extension remains intentionally unbound, so this proof covers explicit isolated CLI publication plus ordinary native `ask`, not normal-HOME binding acceptance. Use each run's own session and agent identity. Never bind to the producer's real Flow or publish to a production tracker. Tell Headless runs to label recommendations as non-consent. Save stdout, stderr, exit code, command, model, thinking level, prompts, overlays, transcripts, and captured Flow artifacts.
4. Step `architecture-agreement-scenarios`: Drive the scenarios below through the selected grill. Grade actual decisions and artifacts against the stated requirements, not instruction strings, exact wording, artifact names, or bare file existence. Model-run findings are observed evaluations, not deterministic unit-test guarantees.

| Scenario input | Observable proof |
|---|---|
| One module has an unsettled tenant-isolation or acknowledged-write durability choice. | The assessment identifies the affected guarantee and expands despite the small edit. |
| A behavior-preserving rename touches many callers. | The assessment grounds no expansion without a new brief or compulsory diagram. |
| An ordinary feature follows an accepted pattern with unchanged access, lifecycle, and failures. | The assessment records the pattern's fit without repeating settled choices. |
| A provider keeps the same method shape but changes residency or recovery obligations. | The grill checks assumptions and exposes the real consequence rather than treating signatures as equivalence. |
| The user proposes caching for vague future speed and has not read the existing path. | Grounding investigates actual facts and clarifies requirements without inventing a scale target. |
| A credible workload or crash scenario establishes an important guarantee, without production measurements. | Analysis can reveal a real trade-off. Missing benchmarks alone do not dismiss it. |
| Greenfield work has either settled local-only context or consequential local-versus-hosted constraints. | Context, not greenfield status, determines expansion. No investigation of nonexistent code is required. |
| A consequential fork has genuinely different viable shapes. | Captured comparable visuals, screening, explicit accepted costs, rejected alternatives, and a recommendation support the question. |
| Signed constraints leave only one shape but recovery consequences remain unagreed. | The shape and exclusions are explained without fabricated viable alternatives. The remaining consequence still needs agreement. |
| Prior explicit answers settle an expanded direction. | The Architecture brief preserves the actual guarantees, interactions, ownership, constraints, rationale, costs, and provenance. It leaves signatures and private coding choices to implementation. |
| No live answer is available, or an actual tool response reports cancellation, timeout, or an empty response. | The corresponding decision stays unresolved. Automatic picks and recommendations are not called user agreement. Preserve the actual response status rather than fabricating a timeout or cancellation. |

5. Step `architecture-agreement-page`: For page proof, inspect the live Nuxt Flow in the browser. Verify the read-scoped `content` endpoint's Flow, revision, question identities and authored context, not just its shell. Check the assessment and agreement content, question-local Mermaid visuals, and answer provenance. Wait for the actual diagrams to finish drawing and retain any failure. Preserve source hashes, the ARIA snapshot and full-resolution lossless WebP through the Verify skill's Evidence step 5. An unavailable browser check is missing proof, not a passed visual review.
6. Step `architecture-agreement-live-smoke`: Run the live smoke separately with the user present. Start a fresh interactive TUI with a disposable grill scenario, a real consequential choice, and no implementation or publication authorization. Publish the generated question, alternatives, trade-offs, recommendation, and necessary captured Mermaid source together through CLI `submit`. Pass the receipt's `ask.html` unchanged to ordinary `ask` and record the answer separately, as flow-page's "Every ask in a Flow" contract says. The bound native extension owns link presentation through its UI-only Flow panel. The explicit isolated-home actual-model helper below leaves that extension unbound and cannot prove the panel; use the native bound helper in `flow-page.md` for that separate proof. Preserve the actual human answer and its separately recorded provenance, continue to the brief and summary, then observe the stop without a completion link or automatic Flow message. Record the file inventory and transcript showing no source implementation, scaffold commit, automatic next-skill invocation, or tracker publication. Headless recommendations and automated keyboard answers cannot satisfy this step.
7. If this worker cannot obtain the live answer, return the exact generated question, complete options and context, artifact paths, missing decision, and evidence of held dependent work to the parent. Do not claim the live smoke passed. Preserve the held run and patch for continuation with the actual answer.
8. Step `architecture-agreement-consumers`: Collect to-spec and implementation consumers' separate proof when evaluating the whole feature. Record which entry point each input exercised. Inspect the canonical isolated spec for embedded necessary visuals and agreement, and inspect gap scenarios for held synthesis or exposed departures. Do not infer those results from the grill's close.
9. Step `architecture-agreement-cleanup`: Stop only the isolated Flow hosts this evaluation started through their authenticated `host stop --home <isolated-home>` commands. Keep the scenario inputs, outputs, session transcripts, artifacts, and failure evidence. Report each observed result, baseline comparison, limitation, unexercised case, and live checkpoint separately.

### Drive native non-consent

These controller cases exercise the actual Session model with native `ask`. They do not establish human agreement. Keep localhost stub transport proof, actual-model behavior, and live human confirmation separate.

1. Step `architecture-agreement-nonconsent-scenarios`: Snapshot the selected skills and source hashes. Create independent scenarios with genuine unsettled consequential choices. Supply facts and applicable decisions, not a future cancellation, timeout, or expected answer. Neutral case paths must not disclose the controller policy.
2. Step `architecture-agreement-nonconsent-config`: Use skill-creator's Session model and thinking discovery. Set `skills.customDirectories` to `$CHECKOUT/plugin/skills`, disable memory, ignore the installed skill under test and its wildcard form, and include its dependencies. Set both `PI_CONFIG_FILES` and `--config` to the overlay. The helper loads the checkout's package without an ask override. The omp process retains real HOME for credentials and clears inherited session variables. Record normal-HOME discovery, secrets, and binding hashes and nonsecret host identity before launch, without copying secrets.
3. Step `architecture-agreement-nonconsent-isolation`: The helper appends operational guidance selecting its owned `<new-case>/flow-home` through the checkout CLI's existing `--home` flag. Use that explicit home and the child's own session and agent identity on every Flow command. Keep native `ask`'s payload, interaction, and retry unchanged. The normal-HOME extension is intentionally unbound, so normal-HOME binding acceptance remains unproven. Let supported CLI commands start the isolated host on demand. `VSTACK_FLOW_PORT` only selects a startup port; existing discovery takes precedence. Never launch `host.ts` directly, replace normal-HOME discovery, secrets or bindings, stop a normal-HOME host, or stop foreign port 51417. Permit only owned disposable Flow state and scenario output, never the parent's Flow or production tracker writes.
4. Step `architecture-agreement-nonconsent-launch`: Use `scripts/flow-questions-tui.py` as SKILL.md specifies, with `--prompt` and `--config`. Run `cancelled --tern` in the helper-owned window. Run `timeout` and `empty` in the classic TUI. Retain each case's source hashes, overlay, session, native tree or PTY capture, actions, and raw `ask` results.
5. Step `architecture-agreement-nonconsent-responses`: Activate native **Cancel** for the cancellation case. For timeout, leave the form alone and check the result against the case's `ask.timeout`. The controller deadline does not prove timeout. For empty, move to native **Submit** without selecting a value and activate it. If the form's defaults or host prevent a genuine empty submit, record the limit. Do not substitute a selected answer.
6. Step `architecture-agreement-nonconsent-result`: Match the published receipt's ordered question ids to the HTML `ask` control names. Preserve the call, receipt, and actual result. Inspect the JSON keyed by control name, labeled notes or Other words, timeout text, or whole-call cancellation error as applicable. The model records observed responses later through CLI `submit`; `ask` authors no Flow answers. Empty selection alone establishes neither cancellation nor timeout. Report an unrelated failure as unavailable proof.
7. Step `architecture-agreement-nonconsent-grade`: Grade the actual questions, answers, Results, close, transcript, and file inventory. Consequential choices stay unresolved or explicitly non-confirmed. A brief separates facts and proposals from agreement. No automatic pick becomes a decision. Dependent work stays held without source scaffolds, implementation, spec publication, tracker writes, or automatic next-skill invocation. A recoverable blocker leaves its Stage in progress. Native cancellation may abort the turn without a terminal assistant reply. Preserve that result separately from any explicitly labelled no-new-decision continuation.
8. Step `architecture-agreement-nonconsent-browser-cleanup`: Inspect each relevant Flow projection in the real browser. Preserve ARIA and full-resolution lossless WebP. Keep failed attempts and unavailable routes, not just successful cases. Copy Flow exports, deliberately close only the owned fixture, and use authenticated `host stop --home <new-case>/flow-home`. Use the same isolated home for recovery and every other Flow operation. The helper stops its own omp process; the evaluator owns Flow closure, authenticated host cleanup, and the final owned-process check. Compare the recorded normal-HOME hashes and nonsecret host identity after cleanup to prove non-mutation.

`summary.json` reports transport completion, not behavioral acceptance. A missing native round trip, uninspected consumer output, or unavailable browser leaves that coverage incomplete.

## Gotchas

- Keep the persistent session's artifact directory beside its JSONL file. When omp truncates a CLI receipt inline, the helper reads the full stored output named by its `artifactId` metadata and applies the same question-identity checks.
- Skill-load and trigger checks prove selection, not architecture reasoning. A stub model's scripted answer proves neither the assessment nor human consent.
- A Headless run has no human answer even when it reaches a summary. An Architecture brief cannot convert its substituted picks into agreement.
- A prior explicit answer can drive a continuation evaluation, but does not substitute for the live confirmation-and-stop smoke.
- A failed process or unavailable dependency makes that proof unavailable. Keep its raw error and do not grade it as success.
- A baseline may also handle a scenario correctly. Report that observation instead of claiming the changed instructions caused it.
- Tests of exact wording or source strings cannot distinguish these consumer-visible failures. Keep evaluation fixtures and grading outside production tracker writes and unrelated source changes.
