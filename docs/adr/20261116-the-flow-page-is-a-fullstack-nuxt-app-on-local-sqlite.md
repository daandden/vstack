# The Flow page is a fullstack Nuxt app on local SQLite

The user chose this in the `flow-page-fullstack-sqlite-24efcf` grill on 2026-11-16. It amends [ADR 0049](0049-flow-reader-uses-nuxt-with-vite-plus-on-bun.md) and the file storage that [ADR 0044](0044-structured-flow-data-drives-server-rendered-pages.md) built on. These are accepted design decisions, not a claim that the implementation is complete.

The Local Flow host's hand-written Bun router is replaced by one Nuxt app. Its server routes serve server-rendered Flow pages and their JSON endpoints, built ahead of time for Nitro's Bun preset and run by the existing Bun supervisor, runtime manifest, and generation swap from [ADR 20261111-the-installed-flow-host-replaces-itself-on-update](20261111-the-installed-flow-host-replaces-itself-on-update.md). Every release keeps the supervisor's generation launch contract, so an older running supervisor can start it. Flow data moves from per-Flow JSON files to one SQLite file per project under that project's Scratch dir. The CLI and the server reach it through one Drizzle schema over Bun's built-in `bun:sqlite`. The CLI keeps committing contributions in its own transaction, so authoring still commits when the host is off or failing. The host writes only Reader comments and learning progress.

Each Flow is one row holding its State as JSON, with its revision, slug, title, creation time, and closed time in columns. Aliases, bindings, migration identities, id tombstones, Reader comments, and learning progress have their own tables, so polling, `find`, and vstack-clean stop parsing whole states. The Flow model is unchanged. Captured attachment bytes stay content-addressed files beside the database. Automatic schema migrations are strictly additive forever: they add tables, indexes, and nullable or defaulted columns, and never drop, rename, retype, or newly constrain anything. Whichever process opens the database first applies them. Any older SQLite-reading generation keeps reading and writing: the previous one during a swap, one left serving after a failed candidate, one several releases behind, or a plugin downgraded to an earlier SQLite release. A change that cannot be made additively needs its own decision.

Existing JSON Flows import automatically, keeping ids, aliases, revisions, reading positions, bindings, comments, and learning progress. The additive rule protects only code that already reads SQLite, so the cutover from JSON is handled separately. Before importing on a normal home, the new code checks for a running host that does not read SQLite. If one answers, it stops it under the host lock with the existing authenticated stop, and only then imports and starts the new supervisor. In practice this happens at the first update, and again only if a downgraded plugin started an old host. A new host that then fails shows unavailable, never content frozen at import, and submits still commit. This is a product step tied to the storage cutover, not the routine restart that the installed-host ADR rejects. After a Flow's import commits, its JSON state, comments, and learning files are renamed with their bytes unchanged, so a downgraded pre-SQLite plugin refuses that Flow instead of reading a frozen copy. Every SQLite open imports any JSON Flow that still has a state file, so Flows created while downgraded carry forward. The renamed backups are never read and are deleted with their Flow.

vstack-clean lists Flow rows under the unchanged retention rules and user confirmation. It deletes a Flow's row, assets, bindings, comments, learning progress, and JSON backup together, keeps the id tombstone and migration identity, then compacts the database.

web-fullstack's curation stays Cloudflare-only. This server stack is specific to the Flow page. Its frontend follows web-fullstack's frontend choices under [ADR 20261119-the-flow-reader-uses-web-fullstack-frontend-choices-and-the-doop-compact-design](20261119-the-flow-reader-uses-web-fullstack-frontend-choices-and-the-doop-compact-design.md).

## Considered options

- Changing only storage and keeping the Bun router and prebuilt client-only reader. Rejected; the user asked for the fullstack shape.
- NuxtHub's `hub.db`, which web-fullstack curates. Rejected because its SQLite driver is libsql, and the CLI, which writes outside Nitro, would need a second client, a second migration path, and a native driver binary.
- Normalized tables, a side table for Result history, or a contribution log with snapshots. Rejected; measured states are small (median 68 KB, largest 1.78 MB across 162 Flows), and each would change the tested model or add a second source of truth.
- One database for every project. Rejected to keep each project's Flows behind a file boundary, as today.
- Routing every contribution through the host. Rejected because it breaks commit-without-host.
- A schema version gate or host-only migrations. Rejected because each makes pages or submits fail during a plugin update.
- Dropping a column two releases after code stopped using it. Rejected after review: users skip releases or downgrade, and a failed candidate leaves an older generation serving, so the drop can break the generation that is actually running.
- Destructive migrations gated on the schema versions that running generations register. Rejected; it adds registration, renewal, and expiry to the storage contract and still breaks a downgrade.
- Letting the old supervisor swap to the SQLite release with no stop. Rejected; if the candidate fails, the old host keeps serving JSON frozen at import and saves comments that are never read, and an open page keeps it from going idle.
- Deferring import while a pre-SQLite host runs. Rejected; it ships two stores, and an open page can postpone the cutover indefinitely.
- Leaving imported JSON names unchanged and not supporting downgrades. Rejected; a downgraded plugin would read a frozen copy and its writes would be lost on re-upgrade.
- An explicit migrate command for existing Flows. Rejected because open pages would lose their live links until someone migrated them.
- A client-rendered reader. The agent recommended it to keep the fixed-hash CSP and the live poll unchanged. The user chose server-rendered pages. The CSP stays strict: no inline script runs without a per-response nonce or hash.
- Curating local Nuxt on Bun with SQLite in web-fullstack. Rejected to keep one curated server recipe.
