# Skill evals run as headless omp processes, not vstack agents

skill-creator's eval runs each run as its own `omp -p` process instead of a vstack agent. That covers the with-skill and baseline runs, the trigger-query runs, and the blind comparator. Each process starts with the Session model and thinking level, read from the last `model_change` and `thinking_level_change` entries in `$PI_SESSION_FILE`, and with a per-run `--config` overlay that controls which skills it sees. The with-skill and baseline runs start in a temp directory that holds only their inputs, with `--no-rules`. Their overlay turns memory off, ignores the skill under test (`skills.ignoredSkills: [<name>, "*/<name>"]`), and includes only the skills it cites plus any competitors staged on purpose (`skills.includeSkills`). When that list is empty, the run uses `--no-skills` instead. Installed plugins and extensions stay in both runs, so vstack agents exist; anything they add affects both runs equally. The comparator needs no agents, so it runs fully isolated with `--no-skills --no-rules --no-extensions` and memory off. Trigger runs use the real environment in an empty temp directory. Their overlay adds the origin project's skill directories through `skills.customDirectories`, so project skills are listed too. We chose this because an eval measures the skill only when the run sees what the test gives it and nothing else. A `task` subagent always receives the session's discovered skill list, and there is no per-task skill override, so a baseline for an installed skill could load the very skill under test.

## Considered Options

- **`vstack-worker` via `task`**: rejected. It fits the roster and the lint as they are, but a baseline can't be kept away from the installed skill under test, and it inherits `CLAUDE.md`, MCP tools, and the parent's memory state. Task spawning does drop `AGENTS.md`.
- **Isolated roles (ADR 0007)**: rejected. An APFS clone copies the whole repo, the opposite of "a directory with only its input files", and it still receives the full skill list.
- **Judge-gated Fan-out with an inline fallback (ADR 0004)**: rejected. Inline would make the parent, which knows the skill and the expected answer, the subject of its own test.

## Consequences

- A headless run is not a subagent, so it is not Fan-out. Its batch is fixed: no judge, no inline, and no vstack cap. When the user says "sequential" or "no fan-out", the runs go one at a time and stay headless. If `omp` can't run, the step stops.
- A Headless run always uses the Session model, through `--model` and `--thinking`. `task.agentModelOverrides` does not apply to it.
- The House style gains a `headless-run` rule, allowlisted to skill-creator. The lint fails on that form anywhere else. The analyzer, which sees both skills and the mapping, stays a normal `vstack-explorer` spawn.
- Runs pass `--approval-mode yolo`, the mode omp subagents always run in. They write only in temp directories, and evaluation.md's approval rule for runs with outside side effects still applies.
- A candidate description is tested without touching the installed file. The overlay lists the candidate's directory first in `skills.customDirectories`, which outranks a provider skill and keeps the bare name. It also ignores `*/<name>`, which hides the displaced installed copy. A probe showed that only the candidate is listed. An accepted description is applied only in homes skill-creator may edit.
- Selection-only trigger runs read the `SKILL.md` of every skill they would use, then stop before acting. They are scored on load events in the session transcript (a `read` of `skill://<name>` or of its `SKILL.md`), never on mentions of a skill's name.
- `--no-extensions` also drops agents from installed and linked plugins (`omp://task-agent-discovery.md`), so with-skill and baseline runs never use it.
