# House style touches adopt items only through required rows

The House style lives in the root `house-style.yaml`. Each replacement row has a scope. A `required` row covers renames and config paths. Every shipped artifact must follow it, so an adopt item that contains its Upstream phrase fails `check-register.ts`, and the Update proposes switching that item to adapt. An `adapted` row covers omp phrasing. It applies only to adapt, merge, and original text, so adopt items keep their Upstream wording. Adopted Matt skills therefore keep saying `/grilling`, while adapted text says `skill://grilling`. The two forms coexist on purpose. `scripts/update-plan.ts` runs every row the Update uses over both Upstream sides (`effectiveOld` and the new Pin) before `git merge-file`. New Upstream text then arrives already substituted, and the merge base matches the vstack text. The agent applies only the judgment rules: the Fan-out line, the single spawn, and skill references. We chose this so that ADR 0001's hash check on adopt items survives a growing House style, and so that substitutions come out the same on every Update.

## Considered Options

- **One scope: every row applies everywhere**: rejected. A single phrasing row, such as `/grilling` → `skill://grilling`, would switch grill-me, grill-with-docs, and other adopt items to adapt for wording alone.
- **A per-row list of items**: rejected. The lists go stale whenever an Upstream adds an item.
- **The agent applies rows after `git merge-file`**, as first written in "Define the `vstack update` flow end to end": rejected. The result would vary between runs, and every Upstream edit next to a substituted line would become a conflict.

## Consequences

- A new `required` row switches every adopt item that contains its phrase to adapt. This automates the rename cascade.
- `check-register.ts` fails when an artifact contains the Upstream phrase of a row in scope. For adapt, merge, and original text, it also fails on a bare `/<vstack-skill>` token and on Upstream spawn wording outside a Fan-out line or a single-spawn line.
- Migration-only rows (`uses: [migration]`) never run on Upstream text. migrate-to-vstack ships a filtered copy at `references/house-style.yaml`. This replaces setup-vstack's copy after Migration became a separate skill. The copy contains every `from` phrase as replacement data, so the old-phrase scan skips it. `check-register.ts` checks its schema and requires an exact match with the root `uses: migration` rows. The skill refers to old phrases through that file, so the lint needs no other exemption.
- Amended by ADR 0028: Migration is part of setup-vstack again, so the filtered copy moved back to setup-vstack's `references/house-style.yaml`.
- A rule can be `required` too. The first is `ask-tool`, from "Decide how vstack asks the user through omp's ask tool, with a visual page per grilling round": every question the agent puts to the user during a session goes through omp's `ask` tool. Shell prompts, documents and comments written for other people, lesson quizzes, and `argument-hint` frontmatter are not covered. The adopt items diagnosing-bugs, domain-modeling, wizard, teach, and to-questionnaire therefore switch to adapt. A judgment rule has no blind substitution, so its lint is a phrase list in `check-register.ts` (a sentence with a listed asking phrase fails unless it names `ask`), and the Update's agent review flags asking wording the list misses.
- `ask-tool` also says that an answer omp auto-selects when `ask.timeout` fires (marked `timedOut: true`) is never the user's answer. A gate asks once more and then stops without acting, and a grilling question stays open. This is separate from Headless runs, which have no `ask` tool and take the recommended answer on purpose.
