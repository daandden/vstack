Q5Step 4: the reviewers' Fan-out block

Settled in #44: the Safety trigger is checked after step 1; there is a Fan-out block when 2 or 3 axes run; a single remaining reviewer runs as one subagent with no judge; and the Safety prompt runs blast-radius without its step 6. Still open is the exact text, and one invariant that inline could break: Matt runs the axes in separate contexts so that one axis can't mask another.

Proposed text for step 4

### 4. Run the reviewers

The axes that run: Standards; Spec, unless step 2
found no spec; Safety, when the step-1 trigger fired.

**Fan-out gate** (`skill://vstack-fan-out`): parts: one
per axis that runs; size: diff lines and files, plus
spec lines for Spec.
- **fan-out** → one `task` call; `tasks[]` has one item
  per part, each with `agent: "vstack-explorer"`. Each
  `task`: that axis's reviewer prompt below, the user's
  override words, the vstack root.
- **inline** → do every part yourself, in order, from
  the same brief. Finish each axis's report before
  starting the next, and don't revise it after reading
  a later axis.

When only Standards runs, there is no gate: **Spawn**
one `vstack-explorer` via `task` (`agent:
"vstack-explorer"`): the Standards reviewer prompt, the
user's override words, the vstack root. Wait for its
result. If it cannot be spawned, do the review yourself.

**Standards reviewer prompt** (Matt's, unchanged)
**Spec reviewer prompt** (Matt's, unchanged)
**Safety reviewer prompt**: include
- The diff command and commit list.
- The trigger that fired.
- The brief: "Run `skill://blast-radius` on this diff
  and skip its step 6. Return its hand-back in under
  400 words, plus the proof script and its output."

wayfinder: research runners

Upstream: "For each research ticket … spin up a /research subagent to resolve it in parallel, capturing its findings on a throwaway research/<name> branch with a context pointer from the ticket." In vstack each runner is an isolated vstack-worker (ADR 0007). Its clone contains .git, but only working-tree changes come back, as a patchPath. A branch the runner creates therefore dies with its clone.

Q6How the findings reach research/<name>

Option A, recommended, is shown solid. Option B (dashed red) has each runner commit and push research/<name> from inside its own clone. That needs a remote, so a local-only tracker would need a second path.

Recommendation: A, the parent lands from patchPath. There is one path; it works without a remote, uses only boring git, and serializes every branch and tracker write in one place. The landing worktree exists only to hold one new file. ADR 0007 rejected git worktree add for the runners, not for this step.

Q7Does a runner start research's own background agent?

A · runner does research's job itself (recommended)

Brief: "Do skill://research's steps 1–3 yourself; do not spawn its background agent." The inline path uses the same brief, so a parent working several tickets never piles N background agents into the shared checkout.

B · runner invokes skill://research as written

Allowed by ADR 0007 (nested writers), but it costs one extra agent per ticket while the runner has nothing to do.

Q8task.isolation.enabled is off

ADR 0007's consequence says: "A skill that needs an isolated role while isolation is off stops and points at setup-vstack. It never falls back to the shared checkout." Inline research doesn't touch the shared checkout at all: the parent writes straight into the landing worktree (Standard) or under the vstack root (Private).
