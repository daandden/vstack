The vstack agent roster and the shared Fan-out rubric

Explainer for Define the vstack agent roster and the shared Fan-out rubric, part of the map vstack: Matt Pocock skills plus pstack enhancements for omp. This ticket settles which agents ship in plugin/agents/ and what each declares (name, purpose, tools, spawns:, write rights). It also settles the exact rubric that every Fan-out gate line cites and the eval judge applies. Eight questions are open, and each ends with a recommendation. The omp facts come from the 18.6.1 source and the omp:// docs. The Upstream quotes come from the pinned text.

Settled · ADR 0004

Every subagent is a vstack agent

vstack agents have no model field, so they run on the parent's live model. Skill text never spawns task, scout, sonic, or reviewer. Nesting is allowed, and each nested Fan-out step runs its own judgment. vstack agents therefore need the eval tool and permission to spawn vstack agents.

Settled · Fan-out guardrail

spawns: is the runtime backstop

Every vstack agent lists only vstack agents in spawns:, with the default subagent first. The lint in check-register.ts fails when a spawn site omits agent or names an agent outside the roster, and when a block lacks its gate line, its batch, or its fallback.

Q9APFS isolation that keeps Private-mode artifacts

These facts come from the omp 18.6.1 source and confirm what you described:

  • Task isolation (isolated: true) clonefiles the whole repo root, .git included, into ~/.omp/wt/t<hash>/m (crates/pi-iso/src/apfs.rs:103-119). From a linked worktree, omp detaches the clone into a private .git (pi-vcs/src/git/mutate.rs:985-1073). Inside the child, git rev-parse --git-common-dir therefore resolves to the clone's .git.
  • Merge-back is a git delta of the working tree: commits, staged and unstaged changes, and non-ignored untracked files (task/worktree.ts:197-333). Nothing under .git comes back, so Private-mode writes are lost.
  • /wt clones with .git skipped and points .git at the parent's common dir (mutate.rs:731-735), so artifacts written there persist. Task isolation has no option for that, and no setting excludes or shares paths.
  • No filesystem sandbox: a child can write absolute paths outside its clone (tools/path-utils.ts:307-319). Those writes are immediate, and the patch doesn't cover them.
  • Apply: the task tool has no per-call apply. Eval agent() takes per-call isolated, apply, and merge, and it returns patchPath when it doesn't apply (eval/agent-bridge.ts:26-38). Your config has isolation enabled, merge: patch, and apply at its default of true.

The coral path is option A: the parent resolves the vstack root once and passes it as an absolute path, so Private-mode writes skip the clone's copy.

Five roles need isolation: hillclimb workers and compare-attempts runners (each keeps a candidate, and the parent keeps only the best), wayfinder research runners (each on its own research/<name> branch), ship verifiers (each checks out PR SHAs), and the background babysitter (it checks out PR branches while the parent keeps working). None of the five wants its changes auto-applied to the parent. The other roles either read only, or write disjoint files in a tree they already own (the Update stages in the update/* worktree, and research's background agent).

OptionMechanismEffect
A (recommended)The five roles run under omp isolation, spawned with eval agent(..., isolated=True, apply=False). When the parent wants a candidate, it applies that candidate's patchPath. The spawning agent resolves the vstack root once: the absolute <common>/vstack in Private mode, or the repo root in Standard mode. It passes the root in every spawn prompt, next to the override words. Children write vstack artifacts only under that root, never under a recomputed one, and they pass it down. The Private-mode rule gains that line. setup-vstack gains a machine check for task.isolation.enabled. A Fan-out block's batch may then be an eval agent() batch as well as tasks[], which amends the guardrail.You keep APFS speed, and Private artifacts survive at any depth. Nothing lands in the parent unless the parent chooses it. The cost is a second batch form for the lint to accept.
BSame as A, but spawned through tasks[], with setup-vstack setting task.isolation.apply: false machine-wide.Keeps one batch form. It also changes how your own non-vstack isolated tasks behave.
CSame isolation, but children never write Private artifacts. They return the content, and the depth-0 agent writes it.No root to pass down. A nested writer inside a clone (for example, research's background agent under a research runner) has to route its content back through every level.
DThe parent runs git worktree add, which shares .git the way /wt does.Artifacts persist with no extra rule, but there's no APFS speed and no carried dirty state. It's the option you moved away from.

What omp 18.6.1 lets an agent file declare

The parser in src/discovery/helpers.ts reads 12 fields, and it drops unknown fields without an error. These are the ones that matter here:

FieldMeaningConsequence for vstack
name, descriptionRequired. The name is global and has no namespace. The description is shown in full in the task tool's agent list and in /agents.Names must not collide with the bundled task, scout, sonic, reviewer, or security-reviewer (Q2).
toolsWhen omitted, the agent gets every built-in the settings allow. An explicit list gets yield added, and gets task added when spawns is set.The only rights lever (Q3). MCP tools are inherited regardless of the list.
spawnsTakes * or a list. With a list, a nested spawn that omits agent gets the first entry. When omitted, the agent can't spawn at all.Every vstack agent needs it. The order sets the default.
outputA JTD-style schema for structured output. A caller's outputSchema wins over it.Useful where the parent parses a fixed verdict (the ship verifier).
model, thinking-levelWhen omitted, the agent inherits the parent's live model and effort.vstack omits both (ADR 0004).
autoload-skillsInjects the named skills before the first prompt. It doesn't restrict which skills the agent can see.Not needed: children inherit every skill and rule anyway.

There is no frontmatter for isolated, readOnly, permissions, or approval mode. Subagents are always forced into yolo approval. Isolation is only a per-call option (isolated: true), and it requires task.isolation.enabled, which defaults to false. task.maxRecursionDepth defaults to 2: main can spawn a child, the child can spawn a grandchild, and the grandchild cannot spawn.

The shared Fan-out rubric · Q6–Q7

The judge is await judge(state, {fanout: {type: "choice", instructions, criteria: {"fan-out": …, "inline": …}}}), and it returns {choice, probabilities, confidence}. It runs on TypeSafe when credentialed, and otherwise on the tiny or smol chat model. A credentialed native judge that fails does not fall back to a chat model; the call errors. The upstream raw material has no numeric threshold. What it does have:

When in doubt, take the simple path. (pstack how, SKILL.md:20)
Independent workstreams. Disjoint files, services, or layers parallelize. Shared writes serialize. (pstack Feature throughput checkpoint, feature.md:9)
A deterministic lever beats fan-out. If the tool can process every unit in one pass, run it yourself. (principle-build-the-lever, SKILL.md:16)
Both axes run as parallel sub-agents so they don't pollute each other's context. (Matt code-review, SKILL.md:11)

The order of checks (Q7). The coral parts are the rubric and the threshold this ticket fixes. The user's words follow ADR 0004: "fan out" or "in parallel" forces Fan-out, and "no fan-out" or "sequential" forces inline.

Q7The rubric text and the decision rule

The state the judge sees is the same at every gate. A skill fills in only parts, the concrete inputs of that step, each with a size the agent can count (files, diff lines, sources, PRs, hypotheses).

state = {
  "request": <the user's words for this invocation>,
  "skill":   <skill name>,
  "step":    <step name>,
  "parts":   [{"label": …, "size": …}, …]
}

instructions:
  A vstack skill step can hand its parts to subagents that run at the same
  time (fan-out), or the current agent can do every part itself, one after
  another (inline). Fan-out costs startup time, tokens on the same model, and
  a merge step. Judge only from the user's request and the step's concrete
  inputs.

criteria["fan-out"]:
  The parts are independent: no part needs another's result, and no two
  write the same file, branch, or state. None of them is trivially small.
  And at least one of these holds: each part needs substantial reading or
  running (many files, a long command, a live app, a large artifact);
  separate contexts are the point (independent review axes, radically
  different designs, competing attempts, per-PR verification); or the
  parts' raw material together would crowd one context.

criteria["inline"]:
  A part depends on another's result or shares a write target; or every
  part is small (a short diff, a few files, a narrow question, one source);
  or a script could do every part in one pass; or the whole step fits
  comfortably in one context. When in doubt, inline.

order of checks
  1. The user's words decide: "fan out" / "in parallel" → fan-out;
     "no fan-out" / "sequential" → inline.
  2. Cannot spawn here (depth cap) or no eval tool → inline.
  3. judge: fan-out only if choice = "fan-out" and confidence ≥ 0.7.
     Any other result, or a judge error → inline.
OptionThresholdEffect
A (recommended)0.7Borderline jobs go inline, in line with "when in doubt, take the simple path".
B0.6More Fan-out on borderline jobs, with more subagent cost.
C0.8Inline unless the job is clearly complex. Code-review's axes will usually share one context.
