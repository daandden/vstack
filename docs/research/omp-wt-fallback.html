When omp wt add can't clone, and why the Update makes a worktree

Explainer for Q5 and Q6 of Decide how vstack makes every worktree go through omp wt. Facts come from omp 18.8.0 (source 4ef97c8) and a scratch-repo probe run this session. These are suggestions only; nothing is decided yet.

Q5 What omp wt add does, step by step

omp wt add, /wt, and the github tool's pr_checkout all call the same native function. It tries a filesystem clone first. If that isn't possible, it does an ordinary checkout. Every outcome exits 0.

Figure 1. Three ways to get a plain checkout, and only one of them prints anything. Sources: crates/pi-vcs/src/git/mutate.rs:642-671 and cli/worktree-cli.ts:150-168.

So the warning line can't be the test, because two of the three plain outcomes are silent. It is also not a clean signal of failure: omp keeps the first backend's error even when a later backend succeeds. The one reliable test is whether stdout contains Cloned from … via. -q hides that line, so vstack must never pass -q. Nothing records it afterward either: omp wt list --json has no clone field.

As skill text, option A is the same three lines at every site:

omp wt add -b <branch> <path> <base>          # never -q
stdout has "Cloned from … via"   → cloned
otherwise                         → plain checkout:
    this site needs ignored/excluded files?  → git worktree remove --force <path>; stop;
                                               name worktree.clone and setup-vstack
    else                                     → continue (install deps if the site needs them)

Recommendation: A. A fallback only costs ignored and excluded files (Figure 2). Stopping where those don't matter would block every Update and every research landing for a repo on a volume that can't clone, and no setting fixes that (table above). The eighth machine check already covers the one cause a setting can fix. No ninth check.

Q6 What update-plan.ts is, and why it makes a worktree

The Update is /skill:vstack-update, a hidden plugin skill you run inside your vstack clone (Define the vstack update flow end to end). It moves the Pins forward and adapts vstack to whatever changed Upstream. Its first, mechanical step is scripts/update-plan.ts, a Bun script that:

  • fetches both Upstreams into ~/.cache/vstack/upstreams/ and finds the new Pins (the latest Matt v<semver> release, the latest pstack commit);
  • diffs every Decision register row from its baseline, maps changed paths to rows, and detects moved items;
  • runs the House style rows over both Upstream sides and stages fresh adopt copies;
  • creates the Update worktree and prints a JSON plan that the judgment stages (agents) then work through.
Figure 3. The Update worktree keeps unconfirmed edits out of the clone omp loads from. That is the reason it exists, and it is unchanged by this ticket.

Why this ticket touches it

Today #38 writes the workspace as git worktree add, called from inside a Bun script. omp's bash rewrite only sees commands the agent types into the bash tool, so it never reaches this call, and the Update worktree is always a plain checkout. Bun deps then have to be installed before check-register.ts can run.
