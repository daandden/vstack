Background: Fan-out and the same-model rule

The map fixes two rules. Fan-out (several subagents running at once) happens only when you opt in. Every subagent uses the parent's model, with no multi-model routing. A single delegated subagent is not Fan-out.

These two rules hit pstack in different places. Making Fan-out opt-in costs speed: the same steps run one after another. The same-model rule costs model diversity, which several pstack skills treat as the whole point. Opting in to Fan-out cannot give that back.

LevelMeaning (from the workflow survey)
F0No subagents.
F1One delegate at a time. Not Fan-out.
F2Fan-out only on a conditional branch (complex question, big change).
F3Fan-out on the default path, directly or through a called skill.
F4Program scale: fleets of agents, cloud workers.

Q4 · The three Fan-out core skills

Each diagram shows the upstream shape. The orange box marks the part that depends on model diversity.

Fan-out core

swarm reject

What it does
Fan out N parallel cloud workers on slices or on a race, wait for all, return one report.
How it fans out upstream
N workers in one message, environment: "cloud", background. Worker model defaults to grok; inherit-parent is already allowed.
What the same-model rule removes
Nothing about model diversity. What it needs is Cursor cloud agents, which omp does not have.
What vstack already has
omp's own task tool already runs a batch of subagents, gives each an isolated worktree, and caps concurrency with task.maxConcurrency. That is a swarm.
Recommendation
reject vstack would carry a second, weaker copy of a built-in omp capability. When a user opts in to Fan-out, skills call task directly.

Fan-out core

arena adapt

What it does
Several agents attempt the same task independently. A judge scores them against a rubric. The parent picks the best as a base and hand-grafts the best ideas from the others.
How it fans out upstream
N candidates at once (default: one each on claude, gpt, grok), then one cross-judge that should be on a different model family from the parent.
What the same-model rule removes
Model diversity: all candidates and the judge would be the same model. What survives: independence. Each candidate starts from a fresh context, so they still don't copy each other's first idea.
What vstack already has
Nothing equivalent. task can run the candidates, but the frame → rubric → judge → pick → graft discipline is arena's own.
Recommendation
adapt Invoking arena is the Fan-out opt-in, so it fits the rule. Runners and judge use the parent model with fresh contexts, and the text says honestly that it buys independence, not diversity. architect uses it only when the user opts in; otherwise architect writes its sketches one after another.

Fan-out core

interrogate reject

What it does
Adversarial code review: the same diff and rubric go to one reviewer per model family; the parent merges findings into one categorized verdict (act on / consider / noted / dismissed).
How it fans out upstream
One reviewer per configured model, default three, all launched at once.
What the same-model rule removes
Its core. The skill states: The adversarial signal comes from model diversity, not assigned personas. Three same-model reviewers with the same prompt mostly find the same things.
What vstack already has
Matt's code-review already reviews a diff on two axes (Standards, Spec) and deliberately keeps them separate instead of merging into one verdict. blast-radius adds the out-of-diff axis.
Recommendation
reject Under the same-model rule its premise is gone, and its single-verdict output contradicts code-review's design. The overlap ticket's pair "code-review with interrogate" drops interrogate.
