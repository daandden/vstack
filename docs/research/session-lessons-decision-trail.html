The same "apply this lesson" step means four different things. omp skill list --json tells session-lessons which box a skill is in.

Recommended

Box 2 runs as a normal vstack hand edit (a branch in the clone, version bump, CHANGELOG, check-register, a PR). Boxes 3 and 4 become a note, because editing them either flips a Disposition (an adopt item becomes adapt) or gets overwritten.

C · Edit only box 1

Q5′What "Backlog" is, and why it's there

The synthesizer sorts every finding into one of three buckets. Backlog holds lessons that a check enforces better than skill text (pstack step 4, after principle-encode-lessons-in-structure). Example: "never commit .env" belongs in a pre-commit hook, not in a SKILL.md sentence the agent might skip. That's code work, so session-lessons doesn't do it in the moment. It only records it. The boxes 3 and 4 notes from Q4′ land here too.

Recommended

A · List it in the summary only

Backlog items are printed in the final summary, and you decide what to file. Nothing gets posted. This is the simplest choice and needs no tracker routing. (Round 1 recommended filing; your question suggests the filing machinery isn't worth it.)

B · File after approval

The same approval ask covers Backlog. Approved items become issues in the project's tracker, or in the vstack repo for vstack skills.

C · Drop the Backlog bucket

Structural findings become Rejected with the reason structural. Loses pstack's encode-lessons-in-structure step.

Q1Transcript source (both skills)

Both skills need "this run's transcript": session-lessons' lenses mine it, and decision-trail's audit checks the log against it. The catch is compaction. After it, the live history://Main view shows only a summary of the early turns.

The JSONL keeps everything. The live concise view renders session.messages, which is the post-compaction context (history-protocol.ts:400).

Recommended

A · JSONL via PI_SESSION_FILE

The running agent resolves PI_SESSION_FILE in one eval cell and passes the absolute path to every spawn. Readers filter type:"message" entries with a jq recipe kept in the skill.

  • Complete after compaction
  • Works inside subagents (each has its own file)
  • Same shape as pstack: pass a JSONL path
  • Noisier input

No eval tool → pstack's digest fallback.

B · history://Main first, JSONL for gaps

Concise view by default. Switch to the JSONL at a compaction boundary, or when full args or output are needed.

  • Cheaper reads
  • Two sources plus a switch rule
  • "Main" is only the top-level agent, so decision-trail in a subagent needs a third path

C · Ship a render script

scripts/transcript.ts turns the JSONL into compact markdown with full tool args and trimmed outputs.

  • Best reading quality
  • Tied to omp's internal session format
  • Needed by both skills: duplicated or cross-referenced

Q3How a lens decides a skill was used

Every reviewer template keeps only findings about skills the session actually used. In pstack, "used" means a Read of a SKILL.md under three Cursor folders. The omp version:

## Scope to skills and tools the session actually used
...scan the transcript for:
- `Read` tool calls against any `SKILL.md` file (workspace `.cursor/skills/`, user-level `~/.cursor/skills/`, or plugin-installed paths under `~/.cursor/plugins/`)
- `read` calls on `skill://<name>` or on any `SKILL.md` path
- a `/skill:<name>` invocation (a `[skill-prompt]` user message)
- spawn prompts that name `skill://<name>`
- Tool calls that match a skill's documented commands
...
- Routing: `skill://<name>`, OR `tune description: skill://<name>`, OR "new skill: <kebab-name>"
Recommended

A · Transcript signals + omp skill list resolves

Reviewers name skills only as skill://<name>. At apply time, the parent resolves the file and its home with omp skill list --json.

  • No folder list to go stale
  • Covers all 11 providers and future ones

B · Enumerate omp folders

List .omp/skills, ~/.omp/agent/skills, .agents/skills, ~/.agents/skills, .claude/skills, plugin node_modules/*/skills, and so on.

  • Closest to pstack
  • Goes stale with every omp provider change

Q6Lenses and synthesizer

The adoption ticket said the "lenses run in sequence by default". ADR 0004 replaced that default with the judge gate, and this ticket records the correction.

session-lessons under option A: parts = one per lens, size = transcript lines.

**Fan-out gate** (`skill://vstack-fan-out`): parts: one per lens (judgment, tooling, divergent); size: transcript lines.
- **fan-out** → one `task` call; `tasks[]` has one item per part, each with `agent: "vstack-explorer"`. Each `task`: the lens template from `references/<lens>-reviewer.md` with the transcript path, the user's override words, the vstack root.
- **inline** → do every part yourself, in order, from the same brief.

**Spawn** one `vstack-explorer` via `task` (`agent: "vstack-explorer"`): `references/synthesizer.md` with each lens's output inlined, the user's override words, the vstack root. Wait for its result. If it cannot be spawned, do the work yourself.
Recommended

A · Fan-out block + an always-on synthesizer spawn

  • The synthesizer judges from a fresh context, even after inline lenses
  • Dropped: the model table, pstack-models.mdc, and the readonly/MCP paragraph (explorers inherit MCP and are read-only by contract)
  • Kept: the prompt-injection paragraph and "do not modify files"

B · Synthesizer inline when the lenses ran inline

  • One spawn fewer on small sessions
  • The agent that applied the lenses grades its own findings

Q8Where decision-trail's TSV lives

With a relative path, an isolated child would append to its clone's copy, and the parent never sees those rows (ADR 0007).

Recommended

A · pstack in Standard mode, the vstack root in Private mode

  • Standard: pstack verbatim (decisions.tsv in the work dir, or .audit/<task-slug>.tsv when several efforts run, kept out of git unless a reviewer needs it)
  • Private: <vstack root>/artifacts/<topic>/decisions.tsv; committing it needs the user's OK, since it would leave private storage
  • Both: the top-level agent fixes the absolute path once and passes it in every spawn prompt that logs

B · Always under the vstack root

  • One rule for both modes
  • In Standard mode, an artifacts/ folder at the main checkout's root sits outside a linked worktree's branch, which makes "commit it for the reviewer" awkward

Q9What a "run" is in omp

pstack: "A run is one agent conversation, including its later turns and any summary of it. A pickup, a replacement agent, or a new chat starts a new run." A run's first row in an existing log has phase start, and its evidence "names this run".
