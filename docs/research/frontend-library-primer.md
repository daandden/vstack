# Frontend library choices in plain language

Research for issue [#454](https://github.com/daandden/vstack/issues/454), checked on 2026-11-11.

These packages solve different jobs. A component library supplies controls. A CSS tool styles them. A store shares application state, while a query library manages copies of data held by a server. Choosing one does not require installing the rest.

The curated library list and new-project package manager remain undecided. The table explains the candidates, not an approved installation list. Its starting points and tradeoffs are engineering judgments based on the linked official documentation. Existing project tooling stays unless the user requests migration. Nuxt is the settled default for requested new applications, with explicit exceptions for Vue with Vite. Rendering and deployment remain separate decisions.

## What each choice buys

| Job | Candidate or starting point | When no extra library is needed | Useful alternative | Main tradeoff | Official sources |
| --- | --- | --- | --- | --- | --- |
| Reusable UI controls | **Nuxt UI** supplies styled buttons, forms, dialogs, tables, and navigation. It combines Reka UI behavior with Tailwind styling and works in Nuxt or standalone Vue. | Native HTML controls and existing project components cover the task. Complex keyboard and focus behavior is a reason to consider a component library. | **Reka UI** supplies unstyled components with keyboard, focus, and ARIA behavior. You own the appearance. **PrimeVue** is another broad component suite with its own theming. | Nuxt UI provides a coordinated starting design but adopts its styling conventions. Reka gives more design control but leaves more assembly work. PrimeVue has a version-specific licensing decision, not just an API difference. | [Nuxt UI foundations](https://ui.nuxt.com/docs/getting-started), [Vue installation](https://ui.nuxt.com/docs/getting-started/installation/vue), [Reka introduction](https://reka-ui.com/docs/overview/introduction), [PrimeVue](https://primevue.dev/), [PrimeUI licensing](https://primeui.dev/nextchapter) |
| Styling | **Tailwind CSS** generates utility classes for layout, colors, and interaction states. Nuxt UI's documented setup installs and imports Tailwind. | Plain CSS, scoped Vue styles, or the project's existing styling system already solve the problem. | **UnoCSS** is an on-demand utility generator whose presets and custom rules define the available classes. Antfu-inspired Vitesse templates use it. | Tailwind follows its utility and theme conventions. UnoCSS offers preset and rule flexibility. Running both general-purpose utility systems adds overlapping class generation and configuration, so it is not a sensible automatic default. Deliberate coexistence is possible, not a claim of incompatibility. | [Tailwind utility model](https://tailwindcss.com/docs/styling-with-utility-classes), [UnoCSS introduction](https://unocss.dev/guide/), [Nuxt UI installation](https://ui.nuxt.com/docs/getting-started/installation/nuxt) |
| Form state and validation | If Nuxt UI is chosen, **Nuxt UI Form plus Valibot** is one candidate. Form handles submission and error display. Valibot checks values at runtime and infers TypeScript types. Nuxt UI does not include a schema library automatically. | A small form can use reactive values, native input constraints, and explicit validation. Nuxt UI Form also accepts custom validation without a schema package. Server-side validation is still required. | **Zod** is another schema validator and works directly with Nuxt UI Form. **vee-validate** manages form state, validation, and submission independently of the UI, so it can use different controls. | Valibot uses modular functions. Zod uses a method-based schema API and has many integrations. vee-validate is a form manager, not a substitute schema syntax. Adding it beside Nuxt UI Form needs a concrete reason to duplicate form-management responsibilities. | [Nuxt UI Form](https://ui.nuxt.com/docs/components/form), [Valibot](https://valibot.dev/guides/introduction/), [Zod](https://zod.dev/), [vee-validate](https://vee-validate.logaretm.com/v4/guide/overview/) |
| Application state | Start with Vue **`ref` and `reactive`** for component state. Nuxt **`useState`** shares keyed, SSR-friendly state between components and transfers it through hydration. | Component-local state, props, events, or a small Nuxt `useState` composable are enough. | **Pinia** organizes shared state into stores with actions, getters, plugins, and store-focused devtools. | Pinia adds structure when shared application behavior grows. That structure is unnecessary for a few local values. Nuxt `useState` values must be serializable. A module-level user-specific singleton is unsafe across SSR requests. | [Vue state management](https://vuejs.org/guide/scaling-up/state-management), [Nuxt useState](https://nuxt.com/docs/4.x/api/composables/use-state), [Pinia introduction](https://pinia.vuejs.org/introduction.html) |
| Remote data | Nuxt **`useFetch`** loads page data with SSR payload transfer. **`$fetch`** makes requests, including event-driven submissions. | Nuxt's fetching, refresh, loading, and error facilities meet the application's needs. A small client-only Vue app may only need native `fetch` and local request state. | **TanStack Vue Query** manages server-state caching, freshness, background updates, and coordination after changes. It still calls a request function such as `$fetch`. | Nuxt's tools integrate with rendering. Query adds an explicit server-state cache and policies to learn. Avoid two competing owners for the same cached resource. Plain `$fetch` in SSR component setup can fetch again during hydration, unlike `useFetch`. | [Nuxt data fetching](https://nuxt.com/docs/4.x/getting-started/data-fetching), [Vue Query overview](https://tanstack.com/query/latest/docs/framework/vue/overview) |
| Charts | **Unovis Vue** composes chart containers, series, axes, tooltips, maps, and graphs through `@unovis/vue` and its core package. | A number, table, static image, or small custom SVG communicates the data without an interactive chart engine. | **Apache ECharts with vue-echarts** offers many chart types and built-in exploration controls. **Chart.js with vue-chartjs** covers common chart types through a canvas-based engine. | Unovis favors composition. ECharts uses a large options model. Chart.js uses its options and plugins rather than CSS to style canvas content. Choose for actual chart and interaction requirements. Vue wrappers do not remove the need for accessibility, sizing, and SSR planning. | [Unovis introduction](https://unovis.dev/docs/intro), [ECharts features](https://echarts.apache.org/en/feature.html), [vue-echarts](https://github.com/ecomfe/vue-echarts#readme), [Chart.js](https://www.chartjs.org/docs/latest/), [vue-chartjs](https://vue-chartjs.org/guide/) |
| Motion | **CSS transitions and Vue `Transition`** cover ordinary state changes and entering or leaving elements. Vue `TransitionGroup` handles list changes. | There is no useful motion requirement, or CSS and Vue's built-ins already express it. | **motion-v**, Motion for Vue, adds declarative springs, gestures, layout, and scroll animation. **GSAP** offers imperative tweens and timelines for coordinated sequences. | Motion's component model fits state-driven animation. GSAP gives explicit sequence and playback control. Both introduce runtime behavior and integration work. A small hover effect does not justify either package. Reduced-motion behavior and lifecycle cleanup still need attention. | [Vue Transition](https://vuejs.org/guide/built-ins/transition.html), [Motion for Vue](https://motion.dev/docs/vue), [GSAP](https://gsap.com/docs/v3/GSAP/) |
| Icons | **Iconify** provides shared icon data and naming across sets, not one visual style. Nuxt UI registers **`@nuxt/icon`** automatically. Select actual sets such as Lucide, Tabler, or Carbon separately. | A few local SVGs or existing icon components meet the need. | UnoCSS **`preset-icons`** generates CSS icons from Iconify data. A direct icon-set component package is another option when only that set is needed. | Choose the integration separately from the artwork. Local collection packages and explicit bundling can avoid runtime icon requests. Dynamic names need care. Each set has its own license, and mixing sets can produce inconsistent artwork. | [Nuxt UI icons](https://ui.nuxt.com/docs/getting-started/integrations/icons/nuxt), [UnoCSS icons](https://unocss.dev/presets/icons), [Iconify set model and licenses](https://iconify.design/docs/icons/icon-set-basics.html) |
| Localization | **`@nuxtjs/i18n`** configures Vue I18n in Nuxt and adds locale-aware routing strategies. | A single-language application does not need a translation framework. Native `Intl` can handle number and date formatting without managing translated messages. | **vue-i18n** supplies the translation integration directly in standalone Vue, or where the Nuxt routing layer is unnecessary. | These are layered choices, not competing translation engines. The Nuxt module handles framework integration. Direct Vue I18n leaves route and framework wiring to the application. Adding either does not supply translated content. | [Nuxt i18n installation](https://i18n.nuxtjs.org/docs/getting-started/), [Nuxt locale routing](https://i18n.nuxtjs.org/docs/guide/), [Vue I18n introduction](https://vue-i18n.intlify.dev/guide/introduction.html) |
| Reactive utilities | **VueUse** packages reusable Composition API helpers for browser events, storage, preferences, and other recurring tasks. Its helpers handle reactive values and scoped side-effect cleanup. | A native API call with straightforward lifecycle handling is enough, or an existing composable already does the job. | Vue's own reactivity and lifecycle APIs plus native browser APIs. | VueUse avoids repeated reactive wiring. Native APIs avoid a dependency for isolated work. Neither removes browser support, permission, or SSR concerns. Use the relevant helper, not a package installation without a use case. | [VueUse guide](https://vueuse.org/guide/), [VueUse cleanup and reactive arguments](https://vueuse.org/guide/best-practice.html) |
| Linting and formatting | **`@antfu/eslint-config`** is an opinionated ESLint flat config for Vue, TypeScript, and other file types. It handles stylistic fixes and aims to work without Prettier. | The existing toolchain already provides the required checks and formatting. No additional preset is needed merely to match a template. | Existing ESLint and Prettier configuration, or **`@nuxt/eslint`** for generated Nuxt-aware configuration. Nuxt integration and an opinionated preset can also be composed deliberately. | A preset saves rule selection but adopts its conventions and update changes. Prettier formats code rather than replacing code-quality lint rules. Giving conflicting tools ownership of the same formatting causes churn. Preserve existing tooling unless migration is requested. | [antfu config and caveats](https://github.com/antfu/eslint-config#readme), [Nuxt ESLint](https://nuxt.com/modules/eslint), [Prettier versus linters](https://prettier.io/docs/comparison) |

## The dependencies are narrower than a complete ecosystem

Nuxt UI's standard setup brings Tailwind. The antfu-inspired templates use UnoCSS, as recorded in [the separate primary-source stack research](./antfu-frontend-stack.md). Those are independent defaults with one concrete styling decision to reconcile. They do not make VueUse, Pinia, Iconify, charting, or validation choices mutually exclusive. UnoCSS even documents using its icon preset alone beside another UI framework. That is different from installing two full utility presets by default.

Nuxt UI Form can use either Valibot or Zod. Nuxt i18n builds on Vue I18n. Vue Query can call `$fetch`. These relationships explain why some names belong together and why others are alternatives. None establishes an additional Anthony Fu preference.

PrimeVue needs a version-scoped caveat. The [official announcement](https://primeui.dev/nextchapter) applies PrimeUI licensing to PrimeVue 5. Community use has eligibility and renewal conditions. Existing MIT releases remain MIT, and the [public MIT repository](https://github.com/primefaces/primevue#readme) reports security fixes only. Evaluate the intended release and license rather than assuming every version has the same terms.

## Choices still open

The maintainer still needs to choose the curated defaults, including styled components versus headless composition, the associated styling tool, and which task-specific libraries belong in the list. The icon set is a separate choice from Iconify integration. A curated recommendation also need not mean preinstalling a library in every new project.

The new-project package manager remains a separate unresolved choice. Existing `packageManager` declarations and lockfiles win. Scaffolding happens only when requested. This note selects no package manager or library list.

## Limits

This is a role and tradeoff comparison, not an exhaustive survey or an interoperability test. Sources are current official documentation and first-party repositories, supplemented by Context7 queries for Nuxt UI, Vue, and Nuxt. The conditional starting points are recommendations, not measured superiority or accepted defaults. No packages were installed, no builds or tests ran, and no bundle-size or performance benchmark was performed. Version compatibility, project constraints, and applicable licenses still need checking when an implementation is requested.
