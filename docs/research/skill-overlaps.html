How the overlapping Matt and pstack skills combine

Explainer for Decide how overlapping Matt and pstack skills merge, part of the map vstack: Matt Pocock skills plus pstack enhancements for omp. Every quote is taken from the pinned upstream text. Q1 is settled. Q2 to Q7 are open and each ends with a recommendation.

Settled · Q1

Real merges keep the Matt name and base

When two items really merge, Matt's text is the base and pstack content is imported into it. The pstack row gets merge and points at the Matt-named skill.

Rule · ADR 0004

Fan-out in every option below

At a step that would run 2+ subagents, the eval judge chooses. With fan-out, the subagents run at the same time. With inline, the agent at that step does the work itself, with no subagents. Running the subagents one after another is rejected (ADR 0004). The user's words override the judge.

Rule · ADR 0001

The rename cascade

Adopt means byte-identical. If vstack renames a skill, every adopt skill that names it becomes adapt. implement names /tdd and /code-review. improve-codebase-architecture names /codebase-design three times.

Q2 · tdd and tdd

Matt · skills/engineering/tdd

A reference for writing tests worth keeping

This skill is the reference that makes that loop produce tests worth keeping: what a good test is, where tests go, the anti-patterns, and the rules of the loop.
  • Seams agreed first: "No test is written at an unconfirmed seam."
  • Anti-patterns: implementation-coupled, tautological, horizontal slicing.
  • Loop: red before green, one slice at a time; refactoring goes to code-review.
  • Supporting files: tests.md, mocking.md.
  • Covers features and bugs; the description includes "wants integration tests".

pstack · pstack/skills/tdd

A workflow for fixing one bug

When fixing a bug with a clear, cheap test path, make the broken behavior executable before changing production code.
  1. Understand the bug; smallest observable reproduction.
  2. Choose the narrowest executable check.
  3. Write the failing test first.
  4. Run it and confirm it fails for the intended reason.
  5. Smallest fix that preserves nearby contracts.
  6. Rerun.

It also has guardrails and a Final Response that names the failing-before and passing-after evidence.

Q3 · codebase-design and architect

Matt · skills/engineering/codebase-design

Shared vocabulary; a reference, not a session

Shared vocabulary for designing deep modules. Use when … another skill needs the deep-module vocabulary.
  • Glossary: module, interface, depth, seam, adapter, leverage, locality. "don't substitute 'component,' 'service,' 'API,' or 'boundary.'"
  • DEEPENING.md: dependency categories and seam discipline.
  • DESIGN-IT-TWICE.md: "Spawn 3+ sub-agents in parallel", one brief each (minimize, flexibility, common caller, ports and adapters), then compare and recommend.

tdd calls it "a reference to consult, not a session to run". improve-codebase-architecture runs it for vocabulary and for design-it-twice.

pstack · pstack/skills/architect

A workflow that designs and then builds

Sketch types, signatures, and module structure before code, then stay in the loop while implementation fills in.
  1. Ground: run how, and also why if ownership or layering changes.
  2. Sketch: run arena across three model families; at least 2 distinct candidates; screen with design-red-flags.md.
  3. Agree: opt-in only. "Default: proceed directly to implementation."
  4. Implement against the sketch.
  5. Scrap and redesign when friction forms a pattern.

Option A. Callers that want vocabulary never end up in a session that implements. architect's Sketch replaces arena with DESIGN-IT-TWICE.

Fan-out under ADR 0004

  • DESIGN-IT-TWICE: with fan-out, 3+ design subagents run at the same time, one per brief. With inline, the current agent writes each design itself, one brief after another, in its own context.
  • architect's Ground: with fan-out, how and why run as concurrent subagents. With inline, the architect agent runs how and then why itself.
  • compare-attempts (vstack's arena) runs only when the user explicitly asks for it, as the pstack-adoption ticket decided.

Explaining one body of code in conversation

  • Written through unslop; the reply is the explanation, not a report.

Q6 · research

Matt · skills/engineering/research (the whole skill, 3 steps)

Spin up a background agent to do the research, so you keep working while it reads.
  1. Investigate against primary sources; "Follow every claim back to the source that owns it."
  2. Write the findings to one Markdown file, citing each claim.
  3. Save it where the repo keeps such notes.
  • Not Fan-out. ADR 0004: "A single subagent, such as research's background agent, is not Fan-out and always runs as written."
  • Nothing harness-specific. No tool names, no .scratch, no model routing. omp's async task is a background agent.
  • No real overlap with how or why. how explains code at runtime and why reconstructs rationale; neither produces a cited file from outside sources. They share the activity (investigation), not the output.
  • Callers: wayfinder (already adapt), ask-matt (already adapt as ask-vstack), and the research ticket-type label in setup's tracker templates. A rename would touch all of them.

Recommend adopt byte-for-byte as research. The alternative, adapt, would only rewrite "Spin up a background agent" in omp terms. That buys nothing, because the sentence already works in omp.

Q7 · Does code-review call blast-radius?

Matt · skills/engineering/code-review (already adapt)

Two separate axes inside the diff

  1. Pin the fixed point; confirm the diff is non-empty.
  2. Find the spec.
  3. Find the standards, plus a 12-smell Fowler baseline.
  4. Standards and Spec reviewers.
  5. Aggregate under ## Standards and ## Spec. "Do not merge or rerank findings."

pstack · pstack/skills/blast-radius (adapt, standalone)

What breaks outside the diff, proven by running code

Listing the callers is not the job. … The job is the breakage grep won't show you.
  • Find "the one fact it's safe because of"; look past grep (library source, pinned versions, lifecycle timing, wire formats, flags).
  • A 5-rung proof ladder, up to "You ran it" and "reproduced it in the running app".
  • Step 6: "For a big or wide change, run it as an arena." In vstack this becomes compare-attempts, only when asked.

Its own description already names the review case ("reviewing a small diff you don't trust"). Upstream it is explicit-invocation only. It is expensive: walking history and dependencies, plus writing and running a proof script.

Option B. Dashed Safety means "only when triggered". There is no mode where the reviewers run one after another: ADR 0004 rejects that because it pays the full subagent cost and saves no time.
