Part 1 · Playbook vs skill in pstack

Short version. A skill is one reusable capability with its own contract (blast-radius: "find what a change breaks beyond the diff"). A playbook is a recipe for one type of task (Feature, Bug fix, Shipping): an ordered list of steps that calls skills and other playbooks. Playbooks are not standalone. They only work inside poteto-mode, which supplies their router, their shared rules, and their reply style.

Why it matters on omp. poteto-mode is rejected, so its playbooks lose their router and their shared rules. A playbook file without frontmatter is not an omp skill, so omp would never list it. Every playbook that joins therefore needs a new home, and whatever it borrowed from poteto-mode (reply style, subagent rules, autonomy) must come from somewhere else. In vstack, those replacements already exist: the jev-selected principles (ADR 0002), the adapted never-block-on-the-human principle, vstack agents on the parent model (ADR 0004), and omp's own todo tool.

Part 2 · Q1 · Three ways to ship a joined playbook

Option A · suggested

Own flat skill

Each joined playbook becomes plugin/skills/<name>/SKILL.md. It calls the Matt skill it extends instead of editing it. Two playbooks may share one skill (both register rows point at it).

Option B

Fold into the Matt skill

Playbook steps become sections of the Matt skill they extend, e.g. perf strategies inside diagnosing-bugs, PR opening at the end of implement.

Option C

Files under ask-vstack

Keep poteto-mode's shape: plugin/skills/ask-vstack/playbooks/<x>.md, loaded only when the router picks one.

Suggestion: A. It is the only option that keeps Matt's adopted skills byte-identical and lets omp find each workflow on its own. C saves a few description lines but hides every workflow behind one router, which is the poteto-mode shape you rejected. B couples the two Upstreams in one file, which makes every Update harder.

Part 3 · All 23 playbooks

How to read the Fan-out column. The survey was written when Fan-out was opt-in only. Since then, ADR 0004 made Fan-out judge-gated: when a job is big enough, subagents run in parallel on the parent's model. So "lost without Fan-out" mostly shrinks to nothing. What stays lost is model diversity: any step whose value came from a different model family (cross-judges, blind judges, cross-model review).

Where the joined skills plug into the Matt flow

Matt's flow, with the suggested joins in green. Matt skills keep their text; the new skills are called after them, or routed to by ask-vstack.

grill-with-docs→to-spec→to-tickets→implement (tdd, code-review, commit)→open-pr→babysit→ship
diagnosing-bugs→perf-issue·forensics·hillclimb?
improve-codebase-architecture / code-review findings→refactor

Settled after this explainer: the End state (commit, PR opened, merge-ready, or shipped) is asked once, up front, by implement, perf-issue, refactor, and hillclimb; if nobody answers, the flow stops at commit.

Risk to watch: Matt main (past the v1.2.3 Pin) already has a pr skill. If a later Matt release ships it, the next Update has to reconcile it with open-pr.
