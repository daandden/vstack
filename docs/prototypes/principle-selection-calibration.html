Principle selection: what jev probabilities mean, and what omp's auto-thinking teaches

Follow-up for “Decide how pstack principles are delivered” (#33). Settled: select every principle scoring ≥ 0.75, with no cap, triggered by a one-line always-on pointer. This report answers two questions: what a jev probability actually conveys, and whether the technique behind omp's auto-thinking can improve our selection.

1. What a jev probability means

P(yes), calibrated across many cases

A yes/no (noul) answer is one number: the probability that the answer is yes (TypeSafe: Noul). jev is trained with RLCD (reinforcement learning for calibrated decisions), so across many predictions, “outcomes assigned 0.8 should occur about 80% of the time” (TypeSafe: AI primer).

  • 0.75 means that roughly 3 of every 4 cases scored like this truly fit the principle.
  • 0.80 means roughly 4 of every 5.
  • This holds for groups of cases, not as a promise about any single one. A yes/no answer has no separate confidence field.

What TypeSafe says about thresholds

“Thresholds scale with risk … Start with conservative thresholds, test with your own data, and adjust” (TypeSafe: Confidence). The cost of a mistake here is small: a wrong pick means the agent reads one extra principle of about 20 lines, and a missed pick means it doesn't read a relevant one. That low, symmetric risk supports a moderate threshold such as 0.75 rather than a strict 0.9.

Caveat: without TypeSafe credentials, omp falls back to a chat model, and its answers are one-hot: exactly 0 or 1 (packages/ai/src/judgment/text.ts: noul: verdict ? 1 : 0). With the fallback, 0.75 and 0.8 behave the same, and every “yes” passes.

3. Applying those techniques: real runs on the same 7 tasks

All runs used typesafe/jev-1.13.0. v1 is the earlier plain questions. v3 uses the auto-thinking wording:

The state is a user's request to a coding agent. Judge the inherent task, not its phrasing.
Answer yes only if the task clearly falls into the situation below; if torn, answer no. Situation: <question>
criteria.true:  The task clearly is this situation.
criteria.false: The task is not this situation, or only loosely resembles it.

  • v3 pushes scores toward the ends: more near 0, and a clear cluster at 0.8 and above. Sharper questions produce more decisive probabilities.
  • Because of that, 0.75 and 0.8 select nearly the same set. In one of 7 tasks they differed, by one principle (prove-it-works at 0.77 on the flaky test). Your choice of 0.75 costs almost nothing extra.
  • There were no misses on the intended picks, and nothing was selected for the README typo, all without a cap.
  • prove-it-works still scores yes on 5 of 7 tasks, because almost every change should be verified. The omp harness already enforces it (“NEVER yield without a smoke run”). One option is to leave it out of selection and reach it only through citations.

4. Where the selection runs

recommended for now

Skill plus a one-line pointer (your trigger choice)

The always-apply line tells the agent to run skill://principles once at task start. The skill calls judge() in eval with the v3 questions, keeps everything ≥ 0.75, reads those principles once, and names them in the plan.

  • Uses only verified pieces: the eval judge() helper was exercised in this session.
  • Runs once per task, so each principle is referenced once.
  • It depends on the agent following the pointer, and it runs after the agent has read the request.

Harness-side, like auto-thinking

An omp TypeScript extension handles before_agent_start, which receives the user prompt and can return a message to inject. It judges the prompt and injects pointers to the selected principles, skipping any already injected this session so each is referenced at most once.

  • Fully automatic, fires before the first output, and needs no always-on pointer.
  • [INFERENCE, unverified]: the extension API has no judge on its context. The package exports @oh-my-pi/pi-coding-agent/judgment (resolveJudge), but I haven't verified that an extension can import it inside the compiled binary. That would need a spike.
  • vstack would ship TypeScript that depends on omp internals, which is new upkeep on every omp release.
