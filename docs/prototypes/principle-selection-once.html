Principle selection: judge once per task, reference once

Your goal: get what poteto-mode does with principles, without poteto-mode. jev judges once, at the start of a task, which principles fit it. The agent reads only those, once, and plans with them. Nothing keeps re-injecting principles on every output, so there's no drift.

Why not the earlier options

Judged TTSR rules (per output)

These fire on every reply and tool call, all session. That keeps pushing principles into the context, which is exactly the drift you want to avoid.

Always-on index

The whole list sits in the prompt every turn. The agent re-reads trigger lines constantly and decides for itself, with broad triggers pulling it off course.

poteto-mode itself

A sticky mode with a principle index, a model split, and Fan-out triggers. #32 rejected it and handed its principle index to this ticket.

How it works

Task starts
(user request)→ agent runs judge() once: 1 state, 24 yes/no questions→ keep yes ≥ 0.75, top 3 principles
+ typescript-best-practices if TS→ read those skills once
and name them in the plan→ work; no more principle injections

This is poteto-mode's contract (“name each principle that shaped a decision; cite only principles whose SKILL.md you read this session”), except that jev picks the principles instead of the agent scanning an index.

Draft skill (vstack name TBD; needs your approval per the naming rule)

---
name: principles
description: Use at the start of implementation, design, or debugging work to pick the principles that fit the task.
---

1. Write the task as one short paragraph: the user's request plus what you now know about it.
2. In `eval`, call `judge(state=<that paragraph>, questions=<questions.json>)`: one yes/no question per principle.
3. Keep answers with yes ≥ 0.75. Take the top 3 principles by score; add `typescript-best-practices` if its question passed.
4. Read each kept skill once through `skill://<name>`.
5. In your plan, name each principle and the choice it changed. Cite only principles you read in step 4.
6. Run this once per task. Re-run only if the task's scope changes.

The questions live in one reference file next to the skill, one line per principle, written by vstack. An Update flags a question when its principle changes upstream. judge is an omp eval prelude helper: it uses TypeSafe jev when credentialed, and otherwise the smol or tiny chat model.

How the selection gets triggered

recommended

One-line always-on pointer

An always-apply rule of about 30 tokens: “At the start of implementation, design, or debugging work, run skill://principles once.” It carries no principle content, so it can't cause drift.

  • Covers plain sessions too.
  • Needs a rules install path.

vstack workflow skills call it

Adapted workflow skills, such as a debugging or implement flow, run it at their first step.

  • No always-on text at all.
  • Plain sessions and adopted Matt skills never run it.

You invoke it

/skill:principles when you want it, like switching poteto-mode on.

  • Full control.
  • Easy to forget.

What else changes

  • The always-on index and the two gates go away. jev decides relevance per task, so no curated membership is needed. [Needs your confirmation]
  • Citations at skill steps stay. A pointer such as skill://principle-fix-root-causes at a debugging step loads once, when the step is reached, which is also not continuous.
  • typescript-best-practices activates through its own question in the same judge call instead of an index line.
  • No TTSR and no omp settings changes. jev acts only as a classifier, called once per task.
  • Update: flags a question when its principle changes. It can re-run these 7 tasks through judge_batch as a regression check on which principles get selected.
