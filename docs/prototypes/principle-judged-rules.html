Judged principle rules: letting jev decide which principle applies

Your idea: keep citations and an always-on index, and let the jev judge decide which principle should be used. omp already ships this mechanism as judged rules: TTSR rules with a question field. This page explains how judged rules work, what they cost, and what they got right and wrong in a real run with the same judge model.

How it works in omp 18.3.1

Agent finishes an output
(its reply text, or each tool call)→ omp sends one judge request with every principle's question→ jev scores each question from 0 to 1→ ≥ 0.7 → hidden reminder injected
“check this against the principle”

Each principle becomes one rule file. Its body is only a pointer, so the principle text still lives in exactly one place:

---
name: principle-fix-root-causes
question: Does this output suppress a symptom (a guard, a catch, a retry, a raised timeout)
  instead of fixing the underlying cause?
interruptMode: never
---
Read `skill://principle-fix-root-causes` and apply it to what you just did.

Source: docs/ttsr-injection-lifecycle.md §10 at omp v18.3.1. The judge runs after an output completes, never while it streams, so it can't interrupt. omp waits up to 5 s before yielding so that a late verdict still lands in the same run. The reminder uses omp's ttsr-warning.md template: “Rule judge flagged your … as likely violating a user-defined rule … real violation → fix it now; false positive → continue.”

Real run: 6 sample agent outputs × 23 principle questions

This used judge_batch with typesafe/jev-1.13.0, the same model omp's judged rules use, at the same 0.7 threshold. The whole run cost $0.0002. It simulates the judge call only; the TTSR delivery path was not exercised, because ttsr.enabled is off on this machine.

Key differences from an index in the prompt

Reactive, not proactive

The judge sees what the agent already did. That suits corrective principles, which catch a mistake after the fact: fix-root-causes, prove-it-works, attack-the-premise, make-operations-idempotent, laziness-protocol. It fits poorly with planning principles, which should shape work before it starts: exhaust-the-design-space, foundational-thinking, experience-first, redesign-from-first-principles. By the time the judge fires on those, the design is written.

Duplication with the harness matters less

A judged rule stays silent until the agent actually breaks the principle. So a principle the harness already states, such as prove-it-works, becomes an enforcement check rather than a second copy of the rule sitting in the prompt. Gate 2 mostly stops mattering, while Gate 1 becomes “can we write a question that is sharp enough?”

Setup changes your omp settings

On this machine, ttsr.enabled: false and ttsr.judge: "off". vstack setup would need ttsr.enabled: true, ttsr.judge: auto, and a judge role that resolves to TypeSafe jev, which you already have (judge: typesafe/jev-latest). With the judge off, question rules register but never fire.

A second model makes the call

jev, not your session model, decides when a principle fires. The map's Notes rule out multi-model routing for subagents. jev is a classifier, not a subagent, and it never writes code or text. Still, it's a second model in the loop, so this is your call.

Options

recommended

Citations + index for planning principles + judged rules for corrective ones

  • Planning principles reach the agent before it acts, through a small index line.
  • Corrective principles catch mistakes after the fact, with 0 prompt tokens.
  • Harness-covered principles get enforced instead of duplicated.
  • Two mechanisms to maintain and install.
  • Needs TTSR and the judge turned on.

Citations + judged rules for every adopted principle

Your idea as stated: jev decides for all of them, and no index sits in the prompt.

  • One mechanism, full coverage, 0 prompt tokens.
  • Planning principles fire only after the work is done.
  • More noise: 23 questions on every output.

Citations + small index (earlier choice)

  • No omp settings change, and no second model.
  • No safety net for principles outside the index.

What an Update would do

A judged rule's question is text vstack writes, the same as an index line. The Update flags it for review when the upstream principle changes. It can also re-run a stored set of sample outputs through judge_batch, like the table above, as a regression check on hits and false positives.
