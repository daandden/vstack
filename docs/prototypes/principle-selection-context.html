Principle selection: what context jev sees, and the harness extension spike

Follow-up for “Decide how pstack principles are delivered” (#33). Settled so far: v3 question wording, every principle scoring ≥ 0.75 is selected with no cap, prove-it-works stays selectable, citations stay, selection is skipped when the judge isn't jev, and selection runs in the harness. typescript-best-practices is dropped at your request.

1. How omp auto-thinking feeds context to jev

It sends only the current user prompt. The state is { request: preprocessTinyMessage(promptText) } (src/auto-thinking/classifier.ts, v18.3.1). preprocessTinyMessage (src/tiny/message-preproc.ts) does the following:

  • Strips ANSI escapes, paired XML or tool envelopes (<user>…</user>), and fenced code blocks, because small models copy literal noise.
  • Shortens long hex runs, such as commit SHAs, to 7 characters.
  • Middle-truncates to 2,000 characters, keeping 2/3 from the head and 1/3 from the tail with an omission marker.

It sends no history, no repo facts, and no session state. It also has a 4 s timeout; on failure it keeps the last level. By comparison, omp's judged TTSR rules send up to 32,000 jev tokens of content, just under jev's limit of about 33k tokens. So jev can take far more context than auto-thinking gives it.

2. Does more context help? Real run

typesafe/jev-1.13.0, same v3 questions, threshold ≥ 0.75.

CaseState fieldsSelected
followup-barerequestfix-root-causes 0.93, encode-lessons-in-structure 0.86
followup-ctxrequest, recent_conversation, repofix-root-causes 0.98, test-behavior-not-implementation 0.97, attack-the-premise 0.91, encode-lessons-in-structure 0.89, prove-it-works 0.87, never-block-on-the-human 0.76
ts-barerequestprove-it-works 0.82, redesign-from-first-principles 0.81
ts-ctxrequest, repoprove-it-works 0.80, redesign-from-first-principles 0.79
  • Given the conversation, a bare “still failing, try again” gained attack-the-premise (0.91), because jev could see the two earlier timeout bumps. It also gained test-behavior-not-implementation and prove-it-works. With the request alone, jev can't know earlier fixes failed.
  • Follow-up prompts are common in real sessions (“still broken”, “now do the same for X”). Without history they are nearly unjudgeable.
  • More context also added never-block-on-the-human (0.76), a marginal pick.
  • A meta-instruction inside the prompt shifts scores. In the spike, “list every skill:// URI …” lowered attack-the-premise from 0.95 to 0.64. Preprocessing helps, but it can't remove that effect.

Proposed state (JSON)

{
  "request":             preprocessTinyMessage(prompt),            // same as auto-thinking
  "recent_conversation": last N user/assistant text turns, each preprocessed,
                         tool output excluded,                      // from ctx.sessionManager
  "repo":                { "languages": file-extension counts },  // from git ls-files in ctx.cwd
  "already_selected":    principles injected earlier this session  // not judged; used to skip re-injecting
}

Kept well under 32k jev tokens. The value of N (for example, 6 turns) and the repo facts are tuning knobs for the build, not decisions.

3. Spike: an omp extension can do this (verified)

This ran on omp 18.3.1 on this machine, from /tmp/vstack-proto/.omp/extensions/principles-spike.ts:

  1. pi.on("before_agent_start") receives the prompt.
  2. ctx.modelRegistry.find("typesafe", "jev-latest") plus ctx.modelRegistry.getApiKey(model) resolve the model and key. ctx.models.resolve does not return jev, because it lists chat models only.
  3. A direct POST https://api.typesafe.ai/v1/systemone with noul questions returned 200 with answers. Note the wire type is noul; the eval helper's bool is an alias.
  4. Returning { message: { customType: "vstack-principles", display: false, … } } injected the pointer. Asked what skill:// URIs followed its message, the model answered skill://principle-fix-root-causes.
  • No omp internals are imported. The extension uses only the public extension API and TypeSafe's public HTTP API, which is lower upkeep than importing resolveJudge.
  • vstack ships TypeScript for the first time. Setup must install it into ~/.omp/agent/extensions/, because the skills CLI won't. That's an input for “Define what vstack setup does” (#39).
  • It adds latency before each turn; the spike used a 4 s timeout, like auto-thinking.

4. How often it judges, and how often it references

recommended

Judge every prompt; inject only new principles

Every user prompt is judged, which is cheap (about $0.0001). Only principles not already injected this session are injected. Each principle is referenced at most once per session, and a new direction in the conversation can still pull in a new principle.

Judge the first prompt only

The judge runs once per session, and the result stands. This has the least noise, but a session that shifts from building to debugging never gets fix-root-causes.

Judge every prompt; re-inject every time

Principles are re-referenced whenever they match. That's the continuous referencing you want to avoid.

5. What this replaces

  • The one-line always-on pointer becomes unnecessary, because the extension injects directly. The system prompt carries no principle text at all.
  • ADR 0002 (hidden skills plus a curated index) is superseded: no index and no two gates. Principles stay hidden skills, 1:1 with pstack, and the skill:// citations at skill steps stay.
  • typescript-best-practices changes from adapt (in #32) to reject, at your request.
