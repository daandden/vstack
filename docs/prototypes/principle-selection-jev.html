jev: what it is, how much context it takes, and subagents

Follow-up for “Decide how pstack principles are delivered” (#33). Sources are TypeSafe's public docs and omp v18.3.1 source, linked inline.

1. What jev is

A decision model, not a chat model

jev is TypeSafe's flagship System One model. It “does not generate text, write code, or hold a conversation. It takes a state and a set of typed questions and returns structured answers” (Jev with coding agents).

  • noul: P(yes), from 0 to 1, for a yes/no question. This is what principle selection uses.
  • choice: one option from a set, with a probability for each option and a confidence value.
  • score: a position on levels you define.

It is trained with RLCD (reinforcement learning for calibrated decisions), so its probabilities are meant to match outcome rates across many cases (AI primer).

Current model: jev-1.13.0 (alias jev-latest)

Price$0.042 per million input tokens. Output is free.

Known weak spots (Jev 1.13 jaggedness) and what they mean for principle selection

Weak spotWhat it means here
Literal reading: “answers the question you wrote, not the one you meant”Each principle question must state its exact condition, with boundary cases in criteria. This is why the v3 wording worked.
Large state full of irrelevant detail: “accuracy falls as the state grows with content unrelated to the decision”Send filtered context: the request plus recent text turns, never tool output or file dumps. Just because jev can take 32k tokens doesn't mean we should send that much.
Adversarial content: text in the state can steer the answerMatches the spike, where a meta-instruction in the prompt moved attack-the-premise from 0.95 to 0.64.

2. Maximum context

From TypeSafe's Models page: “64k tokens per request; 32k tokens for state plus the longest question.” jev reads the state once and evaluates every question against it in parallel.

Budget 1: state + the single longest question ≤ 32k tokens

state (up to about 31.7k)
q

Our longest v3 question is about 90 tokens, so the state can use nearly all 32k.

Budget 2: state + all questions together ≤ 64k tokens

state ≤ 32k
23 q

All 23 principle questions come to roughly 2k tokens, so budget 1 is always the binding limit.

  • omp's judged TTSR rules cap content at 32,000 jev tokens. A code comment says “Jev rejects a judgment branch past ~33k tokens (max_tokens_exceeded)” (src/export/ttsr.ts). omp counts tokens locally with its Encoding.Jev tokenizer.
  • omp auto-thinking sends only the cleaned prompt, at most 2,000 characters, which is about 500 tokens.
  • Cost is negligible at any size: a full 32k state costs about $0.0013 per judgment.

Recommended state budget: about 4k tokens

request             ≤ 2,000 chars   cleaned like auto-thinking (no code fences, XML envelopes, ANSI; SHAs shortened)
recent_conversation last ~6 text turns, each cleaned and cut to 2,000 chars; no tool calls or tool output
repo.languages      file-extension counts, a few dozen tokens

That's enough to judge follow-ups (“still failing”) while staying far below the point where irrelevant detail drags accuracy down. The extension can count tokens and trim the oldest turns first. The ~4k figure is a starting point to tune on sample prompts, not a hard number.

A pattern TypeSafe publishes for this exact problem

The Skill suggestion cookbook picks skills for an agent turn from 182 candidates in two steps: rank everything against the turn, then re-check only the top three with their full descriptions. It injects one line: “Relevant to the current request: X. Ignore this if it does not fit.” With claude-haiku-4-5, this cut wrong skill loads from 16.8% to 7.3%, and loads when nothing fit from 9.8% to 4.0%. Our design is the one-step version (23 principles, threshold 0.75). The same “ignore if it doesn't fit” wording is worth copying into our injected message.

3. Subagents: how pstack does it

pstack never gives subagents an ambient principle list

  • Runner briefs name principles by role. architect's references/runner-prompt.md tells each candidate runner which principles govern its design: “per the separate-before-serializing-shared-state principle skill”, boundary-discipline, make-operations-idempotent, laziness-protocol, and minimize-reader-load.
  • Reviewers get lenses, not principles. reflect's judgment, divergent, and tooling reviewers each have a role prompt and produce principles; they aren't fed any.
  • The only agent that loads the full index is poteto-agent, which reads poteto-mode's whole SKILL.md. #32 rejected poteto-mode.

Source: pstack/agents/*.md, skills/architect/references/runner-prompt.md, and skills/reflect/references/*.md at Pin 12d587df.

Why selecting in subagents would hurt

  • A subagent's prompt is a brief the parent wrote, dense with instructions. jev judging that text would pick principles from the parent's wording rather than the real task: the adversarial-content weak spot.
  • Selection in subagents would multiply injections across Fan-out, which is the drift you want to avoid.
  • The parent already holds the selected principles and knows each subagent's role, so it can name the relevant ones in the brief, exactly as architect's runner prompt does.
  • [INFERENCE] omp docs say restricted task and eval children rebind the parent's already-imported extensions, so before_agent_start likely fires in subagents too. The extension would need to detect a child session and skip it. That's for the build to verify.
recommended

Main session only; the parent passes principles in briefs

The extension skips subagent sessions. When a vstack skill writes a subagent brief, it names the selected principles that govern that subagent's role, as skill://principle-… citations. This is pstack's own pattern.

Subagents select for themselves

Each child's brief is judged. Coverage is more automatic, but it judges the parent's wording, and the injections multiply under Fan-out.
