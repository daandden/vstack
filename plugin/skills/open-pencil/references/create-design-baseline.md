# Create a Design baseline

1. Before asking for agreement, use the [live targeting and save rules](../SKILL.md) to save any unsaved changes in the named document. Tie the agreement to the named page and frame node IDs and to the exact saved `.fig` the user sees. Record the full lowercase digest from `shasum -a 256 "$saved_fig"`. Proceed only when the grill records the user's explicit agreement to those frames in those saved bytes.
2. At handoff, hash that saved file and compare it with the digest from agreement. Do not save the document again. OpenPencil can write different bytes on a save without a design edit. A new save needs new agreement. If the agreed file is missing or its digest changed, stop without handing off a baseline. Use its agreed digest as `sha256` below.
3. Use the PikPak folder the user names or the folder recorded with this change's earlier Design baseline. Resolve it to a folder ID before writing. There is no project default. Use the [Settle-or-ask test](../../../rules/vstack-settle-or-ask.md) for an unresolved destination, and use `ask` under skill://flow-page's "Every ask in a Flow" contract or plain `ask` outside a Flow. Return the question to the coordinator when delegated.
4. Use the official PikPak CLI with a `Read & write files` Personal Access Token supplied privately as `PIKPAK_TOKEN` to the CLI process. Keep the token out of command arguments, session transcripts, logs, and files written by vstack. Do not use `pikpak auth token` or a cached login. If the token is missing or expired, stop and have the user supply or regenerate it through their private credential route.
5. List the folder with `pikpak ls "$folder_id" -F json`. Follow every `next_page_token` with `pikpak ls "$folder_id" -t "$next_page_token" -F json`. Match the exact name `$sha256.fig`. If there is one file with that name, select its ID without uploading. If there are several exact matches, stop and report their IDs. If the name is absent, run `pikpak upload "$saved_fig" -p "$folder_id" -n "$sha256.fig" -w -F json`. Require the returned `file_id` and `PHASE_TYPE_COMPLETE`. List the folder again after upload and check that the returned ID has the exact name. The list and upload are not atomic. Report any concurrent same-name or suffixed duplicate you observe, with the relevant names and IDs. If the returned ID is not the unique exact match, stop rather than silently selecting another ID. Never overwrite or remove a candidate to resolve a collision.
6. For either a reused or a new file, run `pikpak download "$file_id" -o "$downloaded_fig"` to a new local path. Hash the downloaded bytes with `shasum -a 256 "$downloaded_fig"`. The digest must match the agreed SHA-256. PikPak's metadata `hash` does not establish this. If the digests differ, stop with the failing step, file ID, expected digest, and observed digest. Leave the remote file unchanged and record no Design baseline. For an unreachable PikPak service or failed authentication, also stop with the step and file ID when known. Use no other store or design.
7. Only after the exact-ID byte check passes, give the current workflow owner the PikPak folder ID for later reuse, the file ID, the full SHA-256, and the agreed frame node IDs. Include the required behaviors mapped to UI SDK, any explicit requirements the editor cannot annotate, and the design tokens mapped to the project's tokens. The spec carries this record, not a local path, PNG, token, or live document reference in place of it.
