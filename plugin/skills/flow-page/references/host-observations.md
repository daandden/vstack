# Local host and read-only observations

Read this reference before configuring an observation adapter, recovering an unavailable checkout, diagnosing host startup or an unavailable reader, changing a host namespace, or presenting the Flow URL.

## Read-only observations

The host observes git and the separately configured Code host and CI service while a page is being read. It never runs the operation strings in project configuration. Observation changes update the open page without changing the authored revision, task completion, requested or reached End state, or Flow lifecycle.

The built-in native adapters support GitHub and GitHub Actions. GitLab has no built-in native observation adapter. A GitLab Code host or CI service remains `unknown` unless its configuration selects the provider-neutral `http-json` contract below. Setup's `glab` workflow commands do not select an observation adapter and are never executed by the host.

Existing `code-host.md` facts `Host: GitHub` and `Repo: owner/repo` select the fixed `gh pr list` adapter. Existing `ci.md` facts `CI service: GitHub Actions` and its own `Repo` select the fixed `gh run list` adapter independently. Repo values can be backtick-quoted as setup writes them. The files live under `docs/vstack/` in Standard mode or `<vstack root>/config/` in Private mode. A Flow's most recently recorded `branch:` alias selects the remote branch. Without one, the adapter reads the checkout's branch. A detached checkout needs a branch alias. Record it with `alias branch:<branch>`.

Worktrees of one project can intentionally share a Flow. Successful authoring or an explicit `bind` registers checkout context under the Flow lock, even with the host turned off. Read-only `show` and `find` do not take ownership away from that context. Observations use the most recently registered available checkout. If a disposable checkout disappears, the host can use another registered checkout. To register a replacement, continue authoring or bind the in-progress Stage from an available worktree. Keep the intended remote branch as a `branch:` alias. Inspect each observation's adapter, source, timestamps, and available `checkout`, `stage`, and `branch` provenance before drawing conclusions. Checkout recovery changes no authored progress or delivery evidence.

The detached host needs `git` and, for GitHub adapters, an authenticated `gh` on its startup `PATH` in the same user's home. Missing credentials, tools, or checkout access are observation failures, never a reason to run setup or log in automatically. Repository and provider errors are not copied into the page. Git reads HEAD, the branch, and tracked working-tree changes with optional locks disabled.

An optional `- Flow observation: <JSON>` line in either configuration file overrides only that service's adapter. `adapter` is `github` in Code host configuration, `github-actions` in CI configuration, or `http-json` for a separate read-only JSON service. The GitHub adapters take `repo: "owner/repo"`. All adapters accept `poll_seconds`, at least `0.1`, default `15`, and positive `stale_after_seconds`, default `120`. Unsupported or absent provider configuration is unknown. Invalid override configuration is unavailable.

For example, a controlled Code host adapter can use:

```text
- Flow observation: {"adapter":"http-json","url":"http://127.0.0.1:43120/prs","poll_seconds":1,"stale_after_seconds":120}
```

The HTTP adapter sends only GET, follows no redirects, and accepts HTTPS or loopback `http://127.0.0.1`. URLs contain no credentials, query, or fragment. The service returns `{ "observed_at": "<ISO timestamp>", "records": [{ "name": "PR 42", "state": "open", "url": "https://..." }] }`. `url` is optional. Code host states are `open`, `merged`, `closed`, or `unknown`. CI states are `passed`, `failed`, `pending`, `cancelled`, `skipped`, or `unknown`. At most 100 records are accepted. Keep secrets out of record names and URLs. There are no configured commands, scripts, write operations, or browser-triggered actions.

Each observation shows its adapter, source, last observation time, and attempt time. `current` means a recent successful read, not a successful build. `stale` keeps a last observation when its freshness period expires or a later read fails. `unavailable` means a read failed with no observation from that source. `unknown` means no configured adapter or no matching records. Empty results do not mean passed checks. A configuration or branch change discards the earlier source's cache. Restarting the host observes again. Observations are not authored evidence or durable workflow history.


## Present the page

Never open the page automatically. The extension presents question links under flow-page's "Every ask in a Flow" contract. The scoped read link stays the same across folder moves and host restarts. The reader needs the host, with no static file instead. When `live.state` is `unavailable`, retain `live.error` as diagnostics and the committed contribution. Apply the own-run recovery rule to host failures: start an absent host, and restart only a host this run started in its own isolated `--home` namespace. Stop for the maintainer before restarting the normal shared host. After repair, retry once with `bound` or `show` for the URL; if that retry fails, report what was tried and the evidence. Never resubmit a committed question just to repair its host. Host unavailability alone does not block asking that committed question under the common contract. `live.state: "off"` means `VSTACK_FLOW_HOST=off` turned the host off, so no reader is available. Result-only replies and completion summaries have no Flow link or path reminder.

An open reader receives committed answers, Results, task changes, and new Stages without a reload. Live refresh preserves the selected reading stop by stable id, URL fragment, reading position, focus, open evidence disclosures, demo state, quiz attempts, and video position. While the host is unreachable, the open reader keeps its last content and says it is reconnecting. The read-scoped `content` route beside the page exposes the content view and its authoritative `reading` order. `historical` references have no invented position or publication revision; `publications` carry both. The reader consumes this same content-owned order.

Readers poll the read-scoped `versions` route for the authored `revision`, independent `observationVersion`, `hostGeneration`, and `readerGeneration`. A host replacement changes `hostGeneration` even when authored content is unchanged. Reader bytes have their own generation. Each reader finishes its requests before scheduling another poll and bounds each request to five seconds. It reads `content` only for a newer authored revision and `observations` only for a changed observation version. Hidden readers use the same finite requests, so correctness does not depend on visibility signals and parked pages do not hold persistent update connections.

The reader and HTTP routes belong to one Nuxt project, built ahead of time for Nitro's Bun preset. The reader remains client-rendered. Its shell and browser assets ship under `skills/flow-page/reader/`, with the self-contained server at `server/index.mjs` inside that directory. The stable `scripts/host.ts` generation entry starts Nitro without changing its home, port, idle, IPC-ready, or hello contract. Nitro's routes serve the capability-scoped shell and endpoints. Shared browser assets stay at `/_flow-reader/`, without the Flow capability, from the host's own origin only. A missing shell or server build makes authoring receipts report `unavailable` with the rebuild command, and the content still commits. Captured HTML runs on the separate artifact viewer listener, which exposes neither Flow data nor host control.

The installed plugin owns the normal per-user Local Flow host. Every normal CLI copy, including one invoked from a worktree, runs the installed code at `~/.omp/plugins/node_modules/vstack/`. Delegation preserves the caller's working directory, arguments, stdin, session, and agent, so project and Stage bindings stay with the caller. A missing installed runtime refuses the command before authoring rather than falling back to worktree code.

To exercise candidate worktree code, pass `--home <isolated-path>` and choose a separate free `VSTACK_FLOW_PORT`. The home must differ from the normal home, including after resolving symlinks. Passing the normal home explicitly still uses installed code. An isolated home has separate Flow storage, discovery, and credentials. Changing only the port does not select candidate code or another namespace.

Two namespaces cannot share a bound port. The default loopback port is `42000 + uid % 10000`. `VSTACK_FLOW_PORT` selects a different port before startup. The running host's discovery record takes precedence until it stops. The normal installed host stages complete runtime generations while its last good generation serves. A shipped hash manifest guards the installed code and reader against incomplete or mixed installations. Only a candidate that starts and authenticates receives new requests. The listener, host identity, credentials, port, and Flow links stay the same. Failed preparation leaves the last good generation serving. Picker presence renews rather than transferring and may be absent until its next ten-second renewal. Replacement does not answer a picker or grant consent.

Explicit isolated development hosts do not auto-replace. A command using different Flow code, reader bytes, or Bun runtime reports incompatibility, and the host keeps serving its startup bytes. Apply the own-run recovery rule before `host stop`: restart only a host this run started in its own isolated `--home` namespace. Stop for the maintainer before stopping the normal shared host, even when this run started it. Managed installed replacement is product behavior, not agent restart authority. Never stop another namespace's host to free a port.

The JSON-to-SQLite cutover is a product exception to routine replacement. Before importing in the normal home, code authenticates the running host and checks its runtime version or the worker's control-authenticated `/.host/storage` route. Only a JSON-only worker's 404 triggers an authenticated stop under the host lock. Import waits for the listener to close. This also works when an old supervisor already forwards to a SQLite worker. A failed new host then reports unavailable instead of serving JSON frozen at import. Explicit isolated homes are not stopped automatically. This grants agents no manual restart authority.

Each project stores its Flows in `flow.db` under its Scratch dir, shared by worktrees. Contributions commit directly through the store in immediate SQLite transactions, even when the host is off or unavailable. Comments, learning, and observation context use the same store. Existing JSON Flows import on database open; their state, comments, and learning files become byte-preserving `*.imported.json` backups. A failed Flow import retries on the next open without blocking others. Backups remain until confirmed Flow cleanup. Cleanup retains the 15-day closed-Flow floor, never offers open Flows, and keeps expired ids and migration identities.

`host status` reports the host without starting it. `host stop` stops only the host authenticated by this home's private credential. A port held by another program or another home's host stays untouched. The private discovery and secrets live under `<home>/.vstack/host/`. Do not attach these files as evidence.

The host stops after 30 idle minutes with no connected reader, publication, or progress sync. `VSTACK_FLOW_IDLE_SECONDS` changes that duration. `VSTACK_FLOW_HOST=off` turns the host off: authoring still commits, and no reader is available until the host runs. Browser links grant read access to one Flow, never authoring, host control, commands, tracker mutations, or merging.

## Session targets and Picker presence

`target --session <id>` reads the main agent's binding, regardless of `--agent`. It creates no Stage or Flow revision. An unbound session returns `{"target":null}` without starting a host. A bound session returns `binding`, `flow`, `stage`, `revision`, `live`, `target`, and `picker`.

When the host serves the Flow, `target` is its live URL with the first asked question's fragment. Without a live Picker presence, or when Ratchet's presence has no question ids, the fragment is the bound Stage. Presence for another Stage never replaces that binding's target. An unavailable or disabled host returns a null target with its `live` status.

`picker` is an opaque identity for the open picker, or null when none is known. It changes when a new picker opens, even if its URL target is unchanged, and stays the same during lease renewal. Consumers can distinguish a picker opening from its closure without following a closure back to the Stage.

The extension owns `picker open --picker <opaque-id> [<question-id>...]` and `picker clear --picker <opaque-id>`. These commands use the session's main binding and never write Flow content. Subagent writes are ignored. Open retains only question ids present in the bound Flow. Clear removes only the matching picker identity, so an older picker cannot clear a newer one.

The host accepts presence writes only at `/.host/picker`, authenticated with its control secret. A Flow's read capability can read `{presences:[...]}` at the page-relative `presence` route, but cannot write it. Each record contains the project `key`, `flow`, `stage`, `session`, `picker`, ordered `questions`, and an `expires` Unix timestamp in milliseconds.

The extension renews a 30-second lease every 10 seconds while the picker is open and clears it on settlement. Expired records count as absent. Host restart discards all presence. Presence work runs independently of the panel and picker, so failure never holds either.
