# Captured attachments, version 1

Read this reference before capturing an attachment, linking a canonical file revision, adding question/Background figures or option previews, or publishing a runnable artifact.

- `attachment`: optional `ref`, required `type`, `caption`, and `origin` (what produced it, such as the command or the browser step), and optional `description`. `caption` is the figure's title: one line of at most 80 characters. The script refuses a longer caption or one with a line break. `description` holds everything else the reader needs about the figure, in the plain-text formatting of other text fields. `type` is `image` (PNG, JPEG, GIF, or WebP), `video` (MP4 or WebM), `svg`, `mermaid` (diagram source), `file`, `trace`, `evidence`, or `artifact`. Give `path`, the file to capture, or `unavailable`, the reason there is none. A `mermaid` attachment may add `focus`, one or two focal Mermaid ids. An `artifact` instead takes `launch` and `revision`, with the runtime fields below. Name each attachment in a Result's `attachments`, a Document `figure`, a Comparison alternative's `attachments`, a Timeline event's `attachments`, a prototype's `artifact`, a question or Background's `figures`, or an option's `preview` in the same contribution.

When you capture bash output, include the producing bash call's `PI_TOOL_CALL_ID` in `origin`, alongside the command. Read the id inside that producing call and preserve it with the output. If a later call submits the attachment, use the saved id, not the submitting call's id. The reader shows `origin` in the figure's `Source` disclosure so the evidence can be traced to the exact call in the session transcript.

## Captured figures

Questions and Backgrounds take `figures: [{ attachment: "<ref or id>" }]`. Options take `preview: { attachment: "<ref or id>" }`. Each attachment reference must resolve to an available, captured `image`, `svg`, or `mermaid`, in the same contribution or an earlier receipt. The reader shows every figure the same way: the caption as a title, then the description, then a closed `Source` disclosure with the `origin` and the attachment's type, availability, revision, source path, and capture time. The caption is also the figure's accessible name. The reader adds no question number to it, so write none. The script assigns figure ids. Wrong-type, unavailable, and missing references are refused atomically. A plain text figure uses `{ text: "<exact excerpt or output>" }` and is escaped, never executed. Historical HTML remains a reader format only.

Every question figure and option preview also declares `kind`, as [Reader needs and Visual kinds](reader-needs.md) says. Background figures do not meet a question's needs. Repeat a captured attachment reference on the question when its Background or Result already shows the same bytes. Draw diagrams through `skill://vstack-figures` and capture their Mermaid source as `mermaid` attachments. The reader draws each one with the pinned Pele, then applies the same Color role pass as the SVG export. It maps the palette paints to Catppuccin Latte on light and Mocha on dark, with no links or images. Theme changes restyle the drawing in place. Roles include explicit source marks and intrinsic person and database kinds. Focus changes only the border to 2.5px Mauve. Existing captures gain these roles without recapture. A stored figure that the role pass refuses still draws without role paints and keeps its focus. Its layout follows that Pele version and the reader's fonts. Mockups, source screenshots, before-and-after views, and tables can use captured images or safe SVGs. A captured Pele SVG from an earlier Flow keeps its bytes, and the reader shows it in the current theme. Source excerpts and usage previews can use escaped text. Keep comparison and measurement Results as typed Results, with their full evidence, and repeat the relevant visual on a question rather than treating a link to a Result as visual coverage.

## Captured revisions

The script reads an attachment's file once, when you submit it, and stores its bytes in the Flow under their sha256. A `{ file }` canonical link records the file's sha256 at that time. Editing a source file later changes nothing on the page. To show the new content, submit the Result again with `revises`.

In Private mode, `{ file }` can also reference a regular file in the owning project's shared `<git common directory>/vstack/domain/`. Use its absolute path from either the main checkout or a linked worktree. The stored canonical root is `vstack-domain`, with a domain-relative path and sha256. Later `revises` submissions resolve that identity without changing the working directory. This records the path and hash, not the private file's contents. It admits neither other repository metadata nor new attachment paths. Existing approval requirements still apply before publishing private content.

A `path` is relative to the working directory, or absolute, and must be a regular file inside the project or its Scratch dir. A path that leaves both, directly or through a symlink, is refused. An image or video must be one of the formats above, and an SVG with scripts, event handlers, embedded HTML, or script URLs is refused.

A `mermaid` file must be UTF-8 Mermaid that the pinned Pele renders and the export's shared Color role pass accepts. Submit refuses unknown roles, two different roles on one element, authored paints in `classDef`, `style`, or `linkStyle`, and `focus` ids without visible owned marks. It also applies the export's other paint and focus rules. The refusal carries the renderer's message, and nothing in the contribution commits. Document code blocks do not receive this role and paint check.

Safe SVGs may begin with an XML declaration and provenance comments. Capture preserves those bytes and their sha256. SVG references must stay within the document, such as `href="#shape"` or `fill="url(#paint)"`. External resources, stylesheet instructions, document type declarations, CSS imports, and executable styles are refused along with active markup. A refused attachment leaves its entire contribution uncommitted.

The script stores evidence byte for byte. Redact it as the producing skill's contract requires before you attach it, for example with every secret replaced by `<REDACTED>`.

## Runnable artifacts

An `artifact` attachment always has `launch`, the real commands or steps a reader runs outside the page, and `revision`, the producer's source revision. Add `unavailable` with a reason when a required runtime or dependency is absent.

- `runtime: "html"` captures a bundle with `bundle: { entry, files }`. `entry` is its HTML entry path. Each file is `{ path, source }`, where `path` is its unique relative URL path and `source` is a regular file in the project or its Scratch dir. Register every resource the bundle needs. Use relative resource URLs. Traversal and paths outside those roots are refused. The captured bundle's content hash replaces the supplied source revision as its attachment revision. Editing source files does not change the captured bundle.
- `runtime: "local-app"` takes `url`, an `http://127.0.0.1:<port>/<route>` URL with no credentials. Start the actual app yourself. The host neither launches it nor keeps it alive. On each page read it checks that the route answers with HTML, without following redirects. The route must permit iframe embedding. Its own backend dependencies remain the producer's responsibility. Record an absent one with `unavailable`.
- `runtime: "terminal"` shows launch steps and availability without pretending to provide a terminal. An artifact with no `runtime` also remains launch-only. Its optional HTTP URL is a reference, not proof that an app is running.

A prototype Result names the attachment with `artifact: "<ref or id>"`. The live host runs captured HTML on a separate loopback origin with an artifact-only read capability. Its sandbox permits scripts but blocks top navigation, forms, popups, and access to the parent Flow. Bundle network access stays on the viewer origin. Local app routes run in a sandbox on their own origin, never the Flow host's origin. Neither origin has an authoring or workflow endpoint.
