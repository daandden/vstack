## 1. Swarm: coverage and races, not synthesis

**Fact.** Swarm frames a done predicate and artifact, chooses partitioned coverage, identical-brief racing, or a mix, and declares `first pass`, `rank all`, or `best-of` before launching a race. N is the total requested workers, **not** the cloud concurrency ceiling. All N launches belong in one message. Each write-producing worker has a separate output. Default workers are `generalPurpose`, background, cloud, with configured `swarm workers` model (otherwise `grok-4.6-fast-xhigh`); a model race can override the model per arm. A non-default pushed starting branch uses `cloud_base_branch`. Local is an explicit exception for on-machine dependencies. Workers return `PASS`, `ISSUES`, or `BLOCKED` with evidence. Dropouts permit N−1 execution, but coverage aggregation still requires a result for **every required slice**, with explicit gaps. The parent drains terminal results and returns one consolidated report. [S1]

**Derived minimum retained value.** Preserve the task shape, predeclared selection rule, isolated writes, evidence-bearing terminal results, explicit missing coverage, and one parent verdict. A generic parallel launcher without these is not the whole workflow. `first pass` does not itself establish a cancellation protocol for losers: the text still says to read terminal results; it does not authorize abandoning worker accounting. [S1]

**Alternatives/losses.** A named session-local adaptation could retain coverage/race semantics with local workers, losing remote VM isolation, access to cloud capacity, and any cloud continuation across a local restart. An unavailable-cloud gate retains the literal upstream placement contract but makes the workflow unavailable. Reducing N changes sample or coverage capacity; reassigning every required slice can preserve coverage but is not the original simultaneous N-worker execution. No alternative is selected here.

## 2. Arena: rubric, independent comparison, graft, then new verification

**Fact.** Arena is multiple attempts at the **same** artifact, not swarm partitioning. The parent derives 3–6 gradeable criteria before launch. Candidates see the task, not the rubric. Each gets the same task, shared grounding, an independent output path (worktree preferred; separate temporary directory otherwise), and must supply rationale including rejected alternatives. Default panel is four entries: Fable, Sol, Grok, Opus. More candidates can cover more design directions; the same model N times is explicitly allowed when generation-bound rather than judgment-sensitive. Missing output is recorded as a dropout. [S2]

After **all candidate writing completes**, exactly one readonly cross-judge sees the rubric and path-labeled candidates. It prefers a family different from the **parent**, not necessarily every candidate. Its reading runs concurrently with the parent's full reading, never with candidates still writing. The parent scores every criterion, compares both rationales on disagreement, picks the easiest base for future maintenance, and records the judge's verdict. It rereads losers, manually integrates worthwhile ideas under one coherent design, and records graft provenance and rejections. Convergence permits no graft. Wild divergence means reframe and rerun, not average. Finally verify the **synthesized** artifact; failure sends the workflow back to framing or grafting rather than a patch over the result. Output is one artifact plus a synthesis note covering base, grafts, rejections, dropouts, and verification. [S2]

**Derived minimum retained value.** Retain a precommitted rubric, independent attempts, complete parent comparison plus separate judge, coherent synthesis rather than winner-only selection, and verification after integration. The judge is an independent **selection** check; it is not proof that the synthesized code runs. A winning candidate's proof cannot establish a subsequently grafted artifact's behavior.

**Alternatives/losses.** A local worktree arena retains the main algorithm because arena itself specifies no cloud requirement. A reduced panel loses breadth; a same-family panel preserves attempt count but loses cross-family independence. A parent-only comparison loses the cross-judge. Winner-only selection loses grafting and rejected-idea accounting. One candidate eliminates the comparative core; retaining the name would need an explicit degraded-mode contract rather than claiming equivalence. These are choices, not recommendations.

### Counts and diversity are separate dimensions

**Fact.** Setup uses one worker per panel list entry, aliases included. `inherit-parent` and `auto` both omit Cursor `Task.model` and use the parent model. Repeated or alias entries still count; they do not prove diversity. The cross-judge pool is a list from which **one** model is selected, unlike runner panels. Swarm N is shape-driven, not panel-list length. [S3] Four default arena entries do not necessarily mean four providers: Fable and Opus are both Claude-labeled entries. Actual family/provider availability must be established separately.

**Derived requirement.** Carry slot count, distinct candidate scope/design direction, actual model binding, family identity, and the judge's independence rule separately. The accepted candidate/reviewer per-slot variants can express distinct bindings without adding one responsibility agent for every model role. This note does not choose those bindings or silently reinterpret aliases.

## 3. Orchestrate: durable program coordination, not a large batch

**Fact.** Orchestrate targets work outliving an individual agent. The local root never writes code; workers handle code and conflicted integration. On cheap repositories the root may mechanically fast-forward/cherry-pick verified commits and push. Optional local durable sub-coordinators own tracks only when one root cannot drain them; each manages a rolling in-flight window of roughly ten, not blocking batches. Workers/verifiers are cloud by default, with local exceptions for machine-bound runtime controls, transcripts, simulator/IDE state, and local-only auth. One writer per worktree/branch. The stated hierarchy is coordinator → track → worker, and the playbook asserts nesting to depth 3 with full nested Task schema including `environment`. This is a **Cursor workflow assertion**, not evidence that OMP supports that depth or equivalent placement. [S4: roles]

The source separates scheduling from bookkeeping. Only Task spawns/resumes/drains agents; `orch` records state and never spawns, waits, or wakes agents. Standing orders accompany every cloud spawn and every resume verbatim. Missing brief fields refuse spawning; dependencies relay upstream context, not merely order. The brief includes goal, writable/forbidden paths, exclusive worktree, context, acceptance, verification, timebox, forbidden actions, report, and standing orders. Later text says never resume-chain a brief: respawn fresh with consolidated scope. A port must not convert the presence of a resume API into permission to ignore that consolidation rule. [S4: roles/brief]

The durable store contains standing orders, append-oriented overview, unit rows, computed frontier, SHA-keyed ledger, completion inbox, gates, decisions, and derived status. Completions enqueue pointers rather than interrupting critical work. Drains classify all pointers, update tables, and refill ready work. A pilot completes the full brief → work → verify → stack → ledger → merge path before scale; cheap repeated units use the first normal unit as the pilot instead of a ceremonial verifier pipeline. Landing begins with the first verified unit. Closure reconciles every child (including abandoned/zombie cases), verifies the real predicate and landed SHAs, audits the trail, and retains the store. [S4: store/steps/drain]

**Fact: verification is proportional here.** A cheap single-command unit may use worker proof plus coordinator spot-checks. Dedicated different-family verifiers are required for expensive, judgment-laden, or high-blast-radius verification, not every trivial unit. Ledger verdicts are `live-ui-verified`, `unit-test-verified`, `type-check-only`, `verifier-blocked`, `verifier-failed`, keyed by PR and head SHA. Behavioral work needs better than type-check-only; CI green is not a verdict; blocked is not pass. A verifier overrides self-report on the same key. New head SHA requires re-verification in this playbook. Output must be externalized immediately when it lands. [S4: verification]

**Fact: stack semantics differ from the autopilots.** Orchestrate uses `gt` as authoritative stack topology, one serialized stacker per stack, cloud restacks, computed frontier generations, and babysitters scoped to immutable generations. Workers do not run `gt` or rebase. PR closes/retargets pass through the stacker; a retro watcher follows merged PRs. The CLI's frontier commands explicitly describe Graphite discovery. Do not merge this contract with the autopilots' explicit no-`gt` base-branch stack contract. [S4: stack] [S5]

**Derived minimum retained value.** Ownership boundaries, executable briefs, a durable evidence/state ledger, ready-work dependency relays, rolling completion draining, current-artifact verdicts, single topology writer, and total worker accounting are separable from cloud scheduling. Plain TSV/JSON files make state portable; they do not make the scheduler durable.

**Alternatives/losses.** Flattening tracks into root-owned workers preserves scoped execution and upward aggregation but loses sub-coordinator autonomy and scalable drain ownership. A session-local program can retain ledger/frontier discipline while explicitly losing restart-surviving workers. Keeping only independent batches loses continuous landing, durable program recovery, and zombie reconciliation. A full durable port requires a proven runtime lifecycle plus equivalent stack metadata operations; copying `orch` is insufficient.

## 4. Lifecycle and wake-chain requirements

**Fact.** Orchestrate probes read-only state, not resumes, because resume restarts idle agents; transcript mtime is not liveness. Silent death gets a synthetic inbox postmortem. Retry by cause: cap/OOM smaller scope; network same scope; tool error different model; unknown once; two retries then abandon and replan. Late zombies reconcile against current frontier and ledger before accepting output. Tree-wide invalidating conditions stop refill while in-flight work finishes. After repeated infrastructure aborts, durable terminal handoff precedes stopping. After Cursor restart local agents are dead but cloud work is described as continuing; recovery is by pushed PR/branch evidence, not old agent ID, with reconstructed local coordinators. [S4: liveness]

**Fact.** Both autopilots arm a continuing `/goal` only after explicit operator go, use roughly 30-minute audit ticks, and immediately transmit zero-writes holds on operator stop. A local root uses a real terminal `/loop`, monitored-shell sleep, and output-notification sentinel. A cloud root uses an “existing cloud-sleeper wake chain.” Ticks reread the execution playbook from trunk and goal, inspect progress via side effects (commits, pushes, PR/check deltas, store reports), stand down overdue no-progress lanes, and immediately replace them. Full also gathers decision trails and runs retro/post-merge comment sweeps. The planning skeleton additionally prescribes a chat status message each tick even without change. [S6] [S7] [S9: arm]

**Boundary of evidence.** The surveyed playbooks require but do not implement a cloud-sleeper service or demonstrate its delivery/restart guarantees. `/loop` and `/goal` are host facilities. Autonomous-run prefers event watchers with a long heartbeat fallback, otherwise a useful fixed interval; an asynchronous completion notification alone is not this scheduler. [S10] The orchestrate CLI is explicitly not a wake engine. [S4: roles]

**Derived capability checklist, not a claim of availability:**

1. Stable job/branch/artifact identities and durable briefs, standing orders, outcomes, and verification receipts.
2. Non-mutating liveness probes distinguished from resume/reattach; expected-runtime/no-progress detection and bounded replacement.
3. Completion delivery or recoverable queue reconciliation, with no unaccounted child on close.
4. Event wake plus heartbeat, periodic audit delivery during idle time, and an explicit survival boundary for sleep, parent exit, host restart, and session loss.
5. Hold/cancel propagation to all writers, observable acknowledgement or proof they stopped, plus exclusion of stale/zombie writes when a replacement owns the scope. The source demands immediate zero writes; a best-effort message does not prove that guarantee.
6. Artifact externalization before worker loss, cold-start reconstruction from durable facts, and current-head checks before accepting late output.
7. Explicit nested-spawn depth and schema support if retaining track agents. Depth limits cannot be inferred from a generic Task tool existing.

**Alternatives/losses.** Full hosted durability, session-bound automated polling, and manual checkpoint/resume are materially different contracts. The latter two can retain evidence discipline but cannot promise unattended multi-day progress or automatic recovery. An unsupported lifecycle should not be advertised as equivalent cloud autopilot. This note does not choose which availability or automation level vstack accepts.

## 5. Autopilot-full and autopilot-stack retain different authority

**Fact: full.** One cloud owner carries each PR from build, first push and ready PR, self-proof, skeptical Bugbot triage, external deslop, no-comments, pre-babysit rebase, babysit-to-green, to merge. Within about 15 minutes it starts an uncommitted `decisions.tsv`, pushes an initial snapshot, and opens the ready PR **before** self-proof. Independent PRs branch from main; sequenced changes normally merge then branch; a genuinely dependent split may use a short private stack. At merge-ready the root uses independent swarm gates, live behavior, receipts/diff audit, and trunk regression comparison. If trunk lacks the feature, record that and gate diff-added behavior and user-visible end state instead of pretending equivalence. Findings return to the owner. Merge is owner-executed only after root verdict plus granted autonomy, at a trunk-current head; operator-designated items remain operator-click only. Truly new pinned gate/budget raises need fresh countersign after proof, unlike drift from values already on main. [S6]

**Fact: stack.** Cloud owners build and babysit similarly, but no owner merges, arms auto-merge, or closes. At exact `STACK-READY` SHA, independent root swarm verification covers gates, a live floor, and receipts/diff audit. A clean result permits append to one linear base-branch stack, not landing. The root alone changes topology, checking remote refs before lease-protected rewritten pushes; owners push only their own branches. Root rebases bottom-up and owners resolve their slice's conflicts. Changed stable base-to-head patch-id requires a fresh code verdict; unchanged patch-id preserves code verdict but current mergeability and CI must still rerun. Deliver every link with verdict to the operator for bottom-up review/landing. Both autopilots resolve `gh` by default or `origin` when installed and able to resolve the repository; neither requires Graphite. [S7]

**Derived minimum retained value.** Separate PR ownership from independent approval, preserve exact artifact identity, make operator-owned items and merge authority explicit, preserve the full/stack distinction, and retain a serialized stack topology owner. Cloud owner placement and durable scheduled audits are additional requirements, not the definition of independent verification.

**Alternatives/losses.** Session-local owners can retain branch ownership, verdict barriers, and operator handoff but lose remote survival/VM isolation. Build-and-report only retains implementation and evidence, but is neither full autonomous landing nor unattended stack stewardship. Disabling publication/merge retains planning and local verification only; that is an explicit capability loss, not a substitute implementation of full autopilot.

## 6. Shipping and babysit are separate workflows

**Fact: shipping.** One independent cloud verifier **per PR**, not one verifier batching PRs, exercises the real surface against parent versus head and posts `PASS`, `PASS+NOTES`, or `FAIL` on its PR. The author cannot be that verifier. Both pass verdicts allow landing. CI and bot approval do not. Land only a contiguous verified bottom-up run and stop at the first gap even if upper PRs passed. Record verdict head, base, and stable base-to-head patch-id; changed patch means reverify, unchanged patch retains code verdict but reruns current CI/mergeability. Prepare/rebase/retarget only the current bottom PR, merge it (or arm it only when asked), wait for actual merge, recompute, then advance. `autoMergeRequest` is not whole-stack readiness or proof of Origin state. A watcher wake is not a merge receipt: re-read forge state. Stop at the verified ceiling; extending it requires another verification pass. [S8]

**Fact: babysit.** Babysit is not cloud-specific by itself. Modes are `drive` (default, to merge-ready), `background` (nonblocking while plan executes), `threads-only` (review comments only), and `check` (one pass; small/docs-only PRs use it). It starts on user request, not automatically on PR opening. One babysitter per stack follows the lowest unmerged PR. It never rebases, retargets, force-pushes, or changes stack topology; conflicts are reported upward and stop that path. It orders conflicts → review threads → CI, batching known fixes into one push wave. Fixes for already-merged owning code become a new follow-up PR rather than rewriting history, the narrow exception to the frozen queue list. [S11]

Forge readiness is authoritative. GitHub uses the provided watcher; Origin uses its own CLI and mergeable/blocker state, not GitHub-specific watcher tokens. GitHub queued `WAITING` with `merge-queue` means report merge-ready and stop babysitting, **not** wait for a merge. Shipping owns that. One fresh build is allowed for classified flake/infra, not repeated job retries; repeated identical failure is reclassified. Stale base is checked rather than called flake. Bot findings require code-grounded triage; real issues use red-first proof on the owning branch. No babysit mode authorizes merge or auto-merge. [S11]

**Derived minimum retained value.** Babysit can be a portable forge-readiness/triage state machine with exclusive ownership and a strict topology/merge boundary. Shipping additionally needs independent behavioral evidence, patch freshness, and serial landing. They may share a watcher but not authority.

**Alternatives/losses.** A one-shot `check` retains visibility and avoids durable watch requirements but loses continued remediation/monitoring. Local independent shipping verification can preserve author independence and parent/head evidence if it can run the real surface, while changing upstream cloud placement and losing per-VM isolation. Replacing verification with CI-only or author proof loses the explicit safety contract. Omitting PR verdict publication loses the public evidence handoff; whether to allow it is a policy decision outside this note.

## 7. Multi-phase-plan hardcodes more than a model default

**Fact.** This playbook produces a plan and stops; execution requires explicit go. It resolves uncertain technical questions through prototypes and records branch/SHA/artifacts, delegates exploration, fills the fixed skeleton, names full/stack/orchestrate, runs `check-plan.mjs`, and returns path plus validator output. It does not authorize implementing during planning. [S9: opening]

For **each PR**, the literal verification bar is unit **and** live **and** perf. It mandates ten live lanes on `grok-4.6-fast-xhigh` at the PR head, each with concrete scenario, screenshot, and pass predicate, one being regression versus trunk. Gates + ten live + perf + audit means **13 named verification lanes per PR**, not ten total. Each live lane has its own cloud VM and boot recipe. The template covers real browser/Electron/web controls, CLI/TUI controls, or repository mobile simulator controls; two surfaces need both. Missing control skill is recorded as risk, not permission to remove live verification. Perf records metric, interleaved trunk/head probe, baseline, and numeric rule; unlike scenarios require absolute added-work and end-state budgets instead of an invalid ratio. Review-gated interactions require screenshots and a 30–60 second video plus operator review. [S9: verification/template]

**Fact: executable coupling.** `check-plan.mjs` line 7 hardcodes `Ten lanes on `grok-4.6-fast-xhigh` at the PR head`; lines 139–146 require that literal, exactly lanes 1–10, screenshot references, and `Pass when`. Lines 132–134 enforce the repeated verification sentence; lines 150–153 require the perf item structure. Program markers include `/goal`, trunk reads, 30-minute cadence, and status message. Changing setup model-role values alone does **not** remove this hardcoding. [S12]

**Derived minimum retained value.** Evidence-addressable tasks, dependency and file ownership, explicit execution/authority mode, resolved uncertainties, behavioral and performance acceptance, and a checked plan are portable. Exact lane count, literal model, VM-per-lane placement, host commands, fixed prose, and validator coupling are separate adaptation decisions.

**Alternatives/losses.** Preserve literal policy and require its model/cloud/control prerequisites; deliberately parameterize both plan and validator while keeping coverage predicates; or keep a clearly limited planning-only workflow without claiming executable upstream conformance. Reducing lanes changes scenario breadth unless all scenarios are retained and reassigned. Replacing ten Grok workers with ten distinct scenarios on another binding changes model policy but not count; using mixed models adds a new diversity policy not required here. Removing performance or live proof reduces the upstream verification bar. No option is selected.

## 8. Independent verification matrix

| Workflow | Required distinction in source | What does not substitute |
| --- | --- | --- |
| Arena | One readonly judge after candidate writes; prefer family unlike parent; parent also reads/scores; final synthesized artifact verified | A race winner, self-scored rationale, or candidate-only runtime proof |

## 9. Portability boundary and explicit non-decisions

| Piece | Portable core, conditional on tools | Cloud/host-specific part or missing guarantee |
| --- | --- | --- |
| Swarm | Shape, evidence, aggregate, coverage accounting | Cursor cloud placement, cloud base branch, remote worker lifetime |
| Arena | Full rubric/comparison/graft/verify algorithm; local worktrees are explicit | Model resolution and readonly enforcement; no intrinsic cloud requirement |
| Orchestrate | Durable files, ownership, briefs, ledger, completion discipline | Depth-3 schema, cloud workers/restacks, restart recovery, Task lifecycle; Graphite frontier adapter |
| Autopilots | Owner/verifier separation, exact-SHA/patch rules, full-vs-stack authority | Cloud owners, recurring goal/wake/audit, immediate writer hold, external control/deslop tools |

This is a requirement inventory, not an OMP support matrix. Local execution is not automatically weaker on correctness, but it changes upstream placement, lifecycle, capacity, and isolation promises. Cloud placement is not proof of independence or permission to publish. Whether to gate, adapt, parameterize, or defer each piece remains open.

## Removal scope after the operator decision

The operator subsequently chose to **remove cloud-dependent related skills**, rather than install unsupported-mode gates. This supersedes gate-based options as the current scope direction; the alternatives above remain a record of capabilities lost, not competing accepted policy. No files in an installed stack have been deleted by this research.

### Clear exclusions from the current upstream workflow set

- `pstack/skills/poteto-mode/playbooks/autopilot-full.md`: cloud owner per PR, cloud/root wake-chain lifecycle, independent cloud-default swarm verification. Removing it loses unattended owner-to-merge execution and root countersign/audit machinery. [S6]
- `pstack/skills/poteto-mode/playbooks/autopilot-stack.md`: cloud owners and wake-chain program, root verification and topology maintenance. Removing it loses unattended construction/verification of an operator-landed stack. [S7]
- `pstack/skills/poteto-mode/playbooks/shipping.md`: expressly one Cursor cloud verifier per PR. Removing this exact playbook loses the built-in independently verified bottom-up landing workflow. Its patch-freshness and independent-verifier ideas remain portable facts, not grounds for silently retaining the cloud workflow. [S8]

### Cloud-dependent current forms with material local content

- `pstack/skills/poteto-mode/playbooks/orchestrate.md`: exclude the **current full program playbook** if applying the removal direction to cloud-backed orchestration. It contains local root/track agents and machine-bound worker exceptions, but its advertised durable program includes cloud workers, cloud restacks and post-restart continuation. Local briefs, ledger, queue accounting and ownership can be salvaged only as an explicit separate adaptation; retaining the original name/claims while dropping cloud would silently change the contract. Loss is scalable persistent program execution, not just placement. [S4: roles] [S4: stack] [S4: liveness]
- `pstack/skills/poteto-mode/playbooks/multi-phase-plan.md`: the **current execution-coupled skeleton** requires a cloud VM per live lane and routes into full/stack/orchestrate. It cannot remain unchanged after those removals. Its paired `pstack/skills/poteto-mode/scripts/check-plan.mjs` enforces the ten-Grok-lane template. Exclude this template and its active validator dependency, or explicitly replace both with a portable planning contract. Choosing between whole-playbook exclusion and preservation of planning-only content is material: wholesale removal loses useful prototype/evidence/dependency planning, whereas a rewrite is additional adaptation scope. Do not remove all planning concepts just because this template embeds cloud execution. [S9] [S12]
- `pstack/skills/swarm/SKILL.md`: **borderline whole-skill deletion**. Default is cloud and the allowed local exception is specifically on-machine access, so the unmodified skill is not a general local fan-out workflow. Whole-skill exclusion follows a broad “cloud-first skills” interpretation but loses useful partition/race/aggregation behavior. Preserving that behavior requires explicitly authorizing a local adaptation, not silently changing `environment`. This is the main skill-level scope ambiguity. [S1]

### Not cloud-dependent by themselves

- `pstack/skills/arena/SKILL.md`: keep out of a cloud-only deletion set. It explicitly permits local worktrees or temporary candidate paths and specifies no cloud environment. Model panels, rubric secrecy, readonly judging, grafting and final verification still require adaptation, but not cloud. [S2]
- `pstack/skills/poteto-mode/playbooks/babysit.md`: keep out of a cloud-only deletion set. Forge readiness/triage can run locally; continued watch needs host support. Remove or rewrite links to an excluded shipping playbook, without silently deleting the useful `check`/`threads-only`/local drive modes. [S11]
- `pstack/skills/poteto-mode/playbooks/autonomous-run.md`: `/loop` and event/heartbeat support are host-specific, not necessarily cloud. Its cloud-independent predicate loop is not automatically excluded by this decision. [S10]
- `pstack/skills/poteto-mode/playbooks/pause-safely.md`: safe-boundary stop, nested cancellation and durable local resume state are not cloud-dependent. [S13]

These are exclusions from a proposed vendored stack, not instructions to delete upstream research evidence. Excluding playbooks also requires updating their router/discovery references and inbound links (including the multi-phase plan skeleton and babysit → shipping handoff); deleting filenames alone leaves dangling execution instructions. The durable graph is the initial dependency inventory, not evidence that every caller was migrated. No caller migration or new local-mode implementation occurred in this planning slice.

### Final operator clarification: retain useful local workflows

The operator resolved the mixed-mode choice: **keep local workflows, remove cloud instructions/references, and drop entirely cloud-dependent skills**. This overrides the whole-skill exclusion alternatives above for independently useful local behavior. The resulting planning boundary is:

- Retain a **local swarm** coverage/race/aggregation workflow; remove cloud placement and `cloud_base_branch` instructions. Keep explicit worker count, isolated writes, evidence and coverage-gap accounting. Do not promise survival outside the local session.
- Retain useful **local orchestration** briefs, ownership, dependency relays, queue draining, durable ledger and frontier rules. Remove cloud worker/restack/recovery promises. Depth-3 nesting and scheduler durability remain host capability questions, not benefits established by stripping cloud text.
- Retain **arena** in full local form; it has no cloud requirement to remove. Retain **babysit** local check/triage/readiness behavior and any supported local watch; repair its handoff references after the shipping decision.
- Retain **local multi-phase planning** (prototypes, evidence, dependencies and acceptance). Remove VM-per-lane boot instructions, cloud-sleeper and removed-playbook references. Its literal ten-Grok policy and validator coupling need an explicit coherent adaptation; removing cloud alone does not select a new model/count or justify removing live/perf evidence.
- **Shipping is not intrinsically cloud-only in its algorithm.** Although the pinned playbook mandates cloud verifiers, its independent non-author proof, patch freshness and serial frontier logic are useful locally. Under the clarification, retain that local workflow by replacing cloud placement with a locally capable independent verifier, rather than deleting the verification/landing algorithm merely because its upstream deployment is cloud. Retaining it does not grant merge authority or waive actual-surface verification.
- Drop the original **cloud-owned autopilot-full/autopilot-stack program forms**, including their cloud-owner and cloud-sleeper instructions, unless the parent plan explicitly identifies a separately supported local owner/audit lifecycle. Their verification and authority rules may be carried into retained local workflows as requirements; this is not permission to reintroduce unsupported unattended cloud/restart claims. A generic task launcher alone is not equivalent full/stack autopilot.
- Retain the cloud-independent predicate loop and safe-pause concepts where local wake/cancel/persistence capabilities support them. No generic removal of arena, babysit, planning, or pause follows from the cloud decision.

The exact artifact cutover remains the parent planner's job. This research changed only this note; it did not delete, install, or rewrite upstream workflow files.
