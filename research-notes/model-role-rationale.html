Revised decision aid · 16 September 2026 · Tier and agent names proposed, not approved

Capability tiers and custom agents for vstack

Model roles say how much capability to allocate. Custom agents say what work to perform. Amp is used only as a structural reference for tiered difficulty — none of its models are copied or suggested as defaults.

For Decide sync contract and central model config schema.

What changed. The earlier code/research/judgment/prose role taxonomy is withdrawn: it mixed responsibilities with model preferences. The Amp model lineup shown previously is also withdrawn as a suggestion. Researcher→standard and reviewer→deep below reflect the user-approved research outcome; the earlier researcher→low / reviewer→low defaults are superseded. Tiers, agents, bindings, and concrete selectors remain proposals until the resolution is recorded.

1. Revised recommendation

Five vstack capability tiers (vstack_tiny, vstack_low, vstack_standard, vstack_deep, vstack_frontier) plus eight agents (vstack-swift, vstack-researcher, vstack-coder, vstack-reviewer, vstack-planner, vstack-scribe, vstack-candidate, vstack-sonic). Researcher defaults to standard, reviewer to deep with a different family from the coder where practical. Tiers live in modelRoles; each agent binds to exactly one tier through task.agentModelOverrides.

2. Amp as structure only

Amp’s dial separates difficulty positions from specialist responsibilities such as search, oracle, and librarian. Only that separation is borrowed: tiers for difficulty, agents for responsibility. No Amp model name, effort label, or routing behavior is carried over, and this report makes no claim to reproduce Amp performance.

All three requested thinking suffixes (:max, :high, :low, :medium, :xhigh) are therefore valid OMP role-value selectors. Bare IDs are used deliberately: OMP resolves an exact bare id before provider-scoped fuzzy matching, and the provider is chosen at setup from live entitlement.

Entitlement, not catalog existence, is the remaining setup check: the ids above exist in the catalog, but the account used at setup must expose them. The earlier report draft wrongly wrote cursor/grok-4.6-high; the canonical OMP form is grok-4.6:high (effort as suffix, not part of the id). Likewise gpt-5.6-luna:max and gpt-6-astra:low|medium|xhigh.

4. Proposed custom agents from matt and pstack

Seven distinct agent identities — not five. The friendly label swift is one agent (fast retrieval/triage), not a shared name for scout, researcher, and reviewer. Each agent below maps to observed delegation in the two stacks. No agent is created by this report; names are proposals for the adaptation to define.

Name collisions that block the user's labels as written. sonic is a bundled OMP agent: vibe-mode always selects the bundled sonic/task definition, never a same-named custom agent, and task.agentModelOverrides.sonic would repoint OMP's fast vibe tier at the comment-editor model. Likewise tiny is a built-in OMP modelRoles entry driving titles, memory, and auto-thinking classification (falling back to smol); an unprefixed role or agent named tiny collides with it. The report therefore uses vstack-sonic / vstack_tiny throughout. Approving bare sonic or tiny must be an explicit intentional override, not a silent default.

Permissions and tools belong to the agent definition, not the tier. Researchers keep needed MCP access rather than inheriting a boolean readonly flag that would strip it; the comment-editor keeps only its explicitly bounded capabilities and never becomes a generic reviewer. That is eight agent identities (seven user-named responsibilities plus the panel runner the seven-set was missing), not seven — the runner gap is fixed by adding vstack-candidate, not by overloading reviewer or coder.

5. Proposed default bindings

Defaults below incorporate the user-approved research outcome (research-notes/researcher-reviewer-model-strength.md): researcher moves to @vstack_standard and reviewer to @vstack_deep. The earlier researcher→low / reviewer→low defaults are superseded. Escalation across standard/deep/frontier is an effort change on one model (gpt-6-astra), expressible per spawn via the task tool's effort hint — no agent×tier variant cloning needed for that ladder. Model changes (e.g. low→standard) still need an explicit variant or rebinding.

AgentApproved defaultEscalate when
vstack-swift@vstack_lowRetrieval reveals conflicting or widely scattered evidence; hand off to researcher rather than upgrading silently.
vstack-researcher@vstack_standardLow only for bounded retrieval with a stronger synthesis owner; deep for difficult causal/history inference or consequential conflicting evidence.
vstack-coder@vstack_standardSubtle invariants or hard performance work; raise the per-spawn effort hint (medium→xhigh) on the same model, or use an explicit variant for a model change.
vstack-reviewer@vstack_deep, prefer a different family from the coder where practicalFrontier for especially costly misses or review of frontier-level work. Standard for narrow low-risk review; low only for a mechanical checklist, never the sole substantive verdict.
vstack-planner@vstack_deepExceptional open-ended planning; per-spawn effort to xhigh (frontier-equivalent effort on the same model). Standard for routine, already-understood plans.
vstack-scribe@vstack_standardDemanding synthesis across conflicting sources; raise effort per spawn.

vstack-sonic@vstack_tinyRarely: uncertain constraint comments invoke researcher/reviewer instead of upgrading the mechanical editor.

6. Native OMP wiring, persistence, and validation notes

Keep tiers and bindings in config/models.yml, loaded as an OMP config overlay. Proposed starting point — not approved configuration:

modelRoles:
  vstack_tiny: "gpt-5.6-luna:max"
  vstack_low: "grok-4.6:high"
  vstack_standard: "gpt-6-astra:low"
  vstack_deep: "gpt-6-astra:medium"
  vstack_frontier: "gpt-6-astra:xhigh"

task:
  agentModelOverrides:
    vstack-swift: "@vstack_low"
    vstack-researcher: "@vstack_standard"
    vstack-coder: "@vstack_standard"
    vstack-reviewer: "@vstack_deep"
    vstack-planner: "@vstack_deep"
    vstack-scribe: "@vstack_standard"
    vstack-candidate: "@vstack_standard"
    vstack-sonic: "@vstack_tiny"
  • Each agent needs a discoverable definition; a YAML key alone creates no worker. vstack-candidate defaults to standard only as a placeholder — real panels bind per-slot models in §7.
  • Quote @ aliases in YAML. A role value may append one thinking selector (:xhigh and :max included — the short docs list is illustrative, the resolver accepts the full effort ladder).
  • The task wire carries a per-spawn effort hint (capped by task.maxSpawnEffort) but no per-spawn model field: same-model escalation (astra low→medium→xhigh) needs no variant agents; only model changes do.
  • Durability: --config overlays are process-local and must be passed on every launch. For a durable default, prefer PI_CONFIG_FILES or a project .omp/config.yml entry pointing at the same file — otherwise the roles silently vanish on any plain omp invocation. The resolution must record which load path is canonical.
  • Missing roles or unavailable models stop affected delegation under the already agreed rule; native fallback is not a substitute. That enforcement belongs to the eventual implementation.

7. Panels need explicit slots, not just tiers

Reviewers bound to the same tier share a model preference but not necessarily model diversity. Panel membership, runner count, cross-judge selection, and any required diversity remain workflow responsibilities under the already chosen explicit-slot approach. Approved approach: keep modelRoles tier-only and express any approved panel-model exception as an explicit agent binding in the same central YAML, so the exception is visible rather than hidden inside a tier name.
